# 模型选型 + 服务架构 · 精炼刷题卡（口播自检版）

> Agent 开发面试的"模型选型 / 服务架构"主题。分两大块：**选型(质量维度)** + **服务架构(硬过滤+运维)**。
> 刷法：只看【题目】录音 → 对【骨架】自检 → 背【一句话】。★备弹是被深挖时的第二发子弹。
> 配套可视化：`model-selection-rag-visuals.zh-CN.html`。

## 题眼（先记这两句）
- **选型**：不是选最强模型，而是用自己业务的 eval 集在承重维度上打分加权、按"**哪种错更贵、错能不能被工程兜住**"分层配模型。
- **漏斗结构**：`① 硬过滤(模态→语言→隐私，布尔一票否决) → ② 样本+质量(eval 量) → ③ 成本最优(Pareto) → ④ 服务架构(按需叠加护栏)`。硬过滤在前是因为 **0 分乘权重还是 0**，塞进加权只会污染打分、浪费 eval 预算。

# 一、模型选型（质量维度）

## Q0 · 总纲【必刷】给一个新业务要你选模型，整个流程是什么？为什么不直接选榜单第一？
**骨架**：先讲精髓(评测驱动+业务加权，不选最强)。六步：定 eval 集(golden+确定性断言+校准 judge)→拆维度定承重与错误代价方向→特性硬闸门筛(schema/本地部署)→同条件跑分(passrate/precision-recall/TTFT-P95/真实 token 成本)→加权求和+画 Pareto→定 fast/pro 分层→上线观测+数据飞轮。反榜单三理由：**数据污染、任务分布不匹配、不含成本/延迟/特性维度**。挂钩：排产 44 用例 golden + rule_pass_rate≥1.0 CI 门禁 = 可交付评测证据。

## Q1 · 【必刷】precision 和 recall 怎么在选型里取舍？举两个方向相反的例子。
**骨架**：先定**错误代价方向**不问"谁准"。recall 优先=漏了不可逆+误报可廉价复核→privacy-gateway 密钥漏判(FN)已外发不可逆，命中硬 block、recall→miss rate=0，误报交 Codex 复核/分级人审。precision 优先=误动作会落地→排产写生产库，`after_preview` 严格 `confirmed is True` 才放行、批量改带 LIMIT 50，"拿不准"建成第三态转人审。类别极不均衡(密钥占 0.1%)**禁用 accuracy**，报 recall/miss rate。

## Q2 · 【必刷】fast/pro 分层"省钱换可靠性"不矛盾吗？净省没省怎么证明？
**骨架**：净收益在 **Pareto 图**上看不是单轮成本。把 token 花在边际收益最高轮次——classify/并行 worker 用 Fast(约 pro 单价 1/3~1/2)、只 plan+verify 用 Main；best-of-N 并行加的是成本不是墙钟延迟。证明：ncx-forge 同 eval 集把"全程 pro"和"分层"各测一遍落到 (passrate,token) 两点，分层点在"**通过率持平、成本更低**"方向支配全程-pro 就是净省；掉通过率又不够便宜会被 dominate 淘汰。

## Q3 · 【必刷】分层前提是难度分类器准。它把难任务误判成简单、静默做错怎么发现和兜底？
**骨架**：最大风险=**误路由静默失败**。三层兜底：(1)分类器单独当指标评，盯 false-simple，不确定偏保守——`parse_complexity` 无法解析默认落 medium 不落 simple；(2)verify 二次把关，medium/high 都过 verify，非显式 PASS 即 fail(fail-loud)；(3)确定性守卫优先(rule_pass_rate/schema/BudgetRule)。**诚实点：simple 路径目前无 verify、风险最高**，改进给它挂廉价确定性检查或抽样复核。

## Q4 · 【必刷】用 LLM-as-judge 打中文自然度/正确性，judge 本身打不准怎么办？
**骨架**：认边界(position/verbosity/self-enhancement bias)。缓解四件套：拆固定 rubric 维度分不整体打、交换顺序消位置偏、reference-guided、多 judge 集成。最关键**留人工标注校准子集验 judge-human 一致率，<0.9 就先修 judge 不信分**。能转确定性判据的(拒答命中率/TTFT/schema 解析率/排产 check_expected ~16 类断言)就不用 judge。

## Q5 · 【补充】数据不出域的合规业务，"本地小模型够不够"vs"必须上云端强模型"怎么决策？
**骨架**：先合规硬门槛二分(数据不出域→只在可本地部署候选里选，一票否决不进加权)。再用**样本曲线**判本地够不够：画本地小模型 k-通过率曲线，看"本地+4 shot"能否顶替"云端大模型零样本"达门槛+schema 校验。两级：本地小模型高 recall 粗筛/脱敏+硬 block，脱敏后才发云端复核(gateway local-first)。留人审出口→精度要求降级为"不能漏升级"，敢用本地 Qwen 27B。

## Q6 · 【必刷 ★已核实】最优 few-shot 数量是多少？加更多示例一定更好吗？
**骨架**：**没有通用最优数字**，且规律比直觉更极端——这条我查证过真实论文，不是拍脑袋。三个反直觉事实：①GPT-3 原论文的 K=10~100 只是"2048 token 上下文塞得下多少塞多少"，从来不是调出来的最优值([Brown et al. 2020](https://arxiv.org/pdf/2005.14165))。②**顺序比数量更致命**：固定 4 个示例只换排列顺序，SST-2 准确率能从 **54.3%(接近随机)跳到 93.4%(接近 SOTA)**，机制是三种偏置——majority label bias(偏 prompt 里高频类)、recency bias(偏靠后答案，`[P,P,P,N]` 这种 3:1 配比反而 ~90% 判 Negative)、common token bias([Zhao et al. 2021, Calibrate Before Use](https://proceedings.mlr.press/v139/zhao21c/zhao21c.pdf))。③**标签对不对不重要**：把示例标签换成随机的，12 个模型(含 GPT-3)上几乎不影响性能——说明示例主要教格式不是教映射([Min et al. 2022, Rethinking the Role of Demonstrations](https://aclanthology.org/2022.emnlp-main.759/))。到 many-shot(百到近万条)更颠覆：大多数任务要堆很多才见顶，但**推理类任务(MATH/GPQA)过 125-shot 反而下降，且这个下降 next-token loss 预测不出来**——"更多示例更好"在推理任务上是假的([Agarwal et al. 2024, Many-Shot ICL](https://arxiv.org/pdf/2404.11018))。**工程落地**：在自己 eval 集画 shot 数-通过率曲线，同 k 多跑几个顺序/seed 看方差，取达标最小 k\*；用"标签打乱还降不降"测试判断——不降说明缺的是格式不是内容，该换模型/加推理链而非加示例。

## Q7 · 【补充】few-shot 曲线陡不就代表模型强吗？为什么可能是缺点？
**骨架**：斜率陡=高度依赖示范，本质是模仿非内化。两缺点：(1)OOD 长尾会塌(用 OOD 子集单独画曲线，in-dist 陡但 OOD 压不上就是这病)；(2)常伴方差大、对 shot 敏感(同 k 跑 N=3~5 看标准差)。真正想要"**截距高(零样本就行)+平台高**"。成本：格式固定活用 k\* 小便宜模型+2 shot 锚定 schema，开放/OOD 活才为高零样本 floor 付费。

## ★备弹（被深挖时）
- **44 条 golden 凭什么代表线上分布？**→ 认账地基风险。三兜底：①覆盖度按业务维度分层抽样(非随机)、每类标难度边界；②用线上真实频次分布反查覆盖率、缺口回流；③数据飞轮持续校准。区分"代表性"(分布对齐)vs"充分性"(量级)，量级不够只报趋势。
- **闭源模型静默升级权重怎么发现？**→ 选型是持续过程。①版本钉死+记 trace(带"哪个版本测得")；②golden 当 CI 定期回归、阈值告警；③金丝雀/影子对比双跑才切；④盯漂移信号(escalation 骤变/改判率升/schema 合法率降)。
- **offline 分高但 online 差怎么闭环？**→ 必然 gap。三成因：分布 gap(飞轮+分层采样)、判据 gap(拿线上信号反向校准维度权重)、环境 gap(补端到端多轮回放)。**离线分是筛选器不是验收章，线上代理指标才是最终 eval 门**。
- **加权求和的权重哪来的？致命维度低分被高分买回不矛盾吗？**→ **分两层**：硬闸门层(schema<门槛/不能本地/miss≠0，布尔淘汰，不进加权)+加权层(只在过闸候选间用)。权重按错误代价方向定序、用代价数据锚定量级(能折钱就折钱)。方向冲突不做线性加权→定主指标+次指标降级成约束，或第三态转人审。**更信 Pareto**(不需精确权重也能淘汰被支配点)。
- **多轮问答/客服这种长上下文场景，能不能靠 many-shot 硬堆示例替代微调？**→ 分任务看，不是万能替代。检索/相似样本类任务(翻译、情感分类)在 SOTA 长上下文模型上能堆到近万 shot 持续涨，效果逼近微调；但**推理/规划类任务(数学证明、代码验证)过了某个 shot 数会反而下降**，且常规的 loss 曲线看不出这个拐点，必须在自己的下游任务指标上实测。另外**顺序敏感在 many-shot 依然没消失**(固定 50 条示例换 10 种顺序，准确率能在 45%~70% 之间大幅波动)，且**模型越大不代表 many-shot 越稳**——没专门做长上下文训练的大模型，效果可能比小模型掉得更快。诚实结论：many-shot 是"额外一个可调杠杆"，不是"微调的免费替代品"，用之前必须先在业务 eval 集上验证该任务是不是"检索型"而不是"推理型"。
- **自己写 eval 又用它选型=对着测试集调参？**→ 认这比数据泄漏隐蔽(人肉梯度下降)。四防线：①三集分离(留 held-out 只定稿前跑一次)；②看跨集稳定性非单集峰值(多 seed 看方差)；③优先确定性判据+简单配置(shot 池小限制过拟合)；④线上分布回流做终极检验。**eval 是用来选和验收的，不是用来训的**。
- **本地 vs 云端不止合规，TCO 怎么权衡？**→ 涉合规=硬门槛一票否决。不涉合规=TCO 非单价：低频/波动/量小→云(养不起 GPU 利用率)；高频/稳定大批量→本地摊薄固定成本(排产夜间批处理即便不为合规也划算)。算隐性成本(云的版本漂移/锁定 vs 本地的能力天花板/自维护)。
- **99.5%/0.9/miss=0 这些阈值哪来的？**→ 分三类：①从错误代价倒推(miss=0 因漏密钥不可逆，业务定义的)；②从下游承受力倒推(schema 门槛看下游能不能 verify 兜)；③统计经验值(judge-human 0.9 是领域常用可信线，标成经验值不硬编，应改用 Cohen's kappa)。

# 二、服务架构（硬过滤 + 运维护栏）

## 题眼
硬过滤是"能不能做"的布尔一票否决；服务架构是选完之后按 **请求量 × 单请求代价 × 后端脆弱性** 任一高才叠加的护栏。铁律：**任何一环失效都落到能用的默认(fast_model 空回退主 model)、出域的永远是脱敏后材料、降级答案绝不冒充正常结果**。

## Q0 · 总纲【必刷】选型流程是什么？为什么模态、隐私排在质量打分前？
**骨架**：四步漏斗(硬过滤→样本+质量→成本→服务架构)。模态/隐私是**存在性问题、O(1) 集合运算**，先跑把候选池从几十砍到几个，昂贵 eval 只在小池子做；不支持某模态准确率就是 0，0 分乘权重还是 0，塞进加权只污染打分解释、浪费预算。

## Q1 · 【必刷】短视频反推 prompt 的链，选全能模型还是拆 ASR/VLM/文本三段？
**骨架**：默认**拆段路由**(ncx-video-agent)：ASR 走 qwen3-asr-flash + DashScope native 端点(音频 base64 内联，OpenAI 兼容 chat 不支持 ASR)；视觉走 qwen3-vl-plus + OpenAI 兼容 chat(帧 image_url data URL，跨厂商通用)；融合纯文本。理由：每段用该模态最优模型，各段 API 契约本就不同。反选全能：量小/链短/无编排运维能力/全能够用。判据=链路长度×调用量×分段质量差 vs 编排+运维成本。补：纯文本任务里 VLM/ASR 第一步就被模态过滤划掉。

## Q2 · 【必刷】privacy-gateway 降级链讲一遍：本地也挂、备也挂，用户看到什么？多 key 轮转和熔断区别？
**骨架**：三档路由(数据敏感度)：local 只本地不出网；review/pro 先本地再脱敏发线上、命中密钥硬 block。降级链：本地出答案→判是否需复核→发 Codex 主 key 轮转(`_is_retryable` 命中 401/403/408/409/429/5xx 才换 key，不可重试立即 break)→主 key 试完才 fallback DeepSeek→再失败按 policy。**终点必须一定能返回且不依赖会失败的下游(纯本地字符串)**：高风险 guarded-fallback 明确拒绝、低风险静态兜底。**轮转 vs 熔断**：轮转=这把 key 限流了换一把(但还会试坏 key)；熔断=连续失败 N 次一段时间直接跳过。**分层超时是命门**：embedding 1.5s / Codex 600s，绝不能都配 600s 否则挂掉的 embedding 把每请求拖 600s 雪崩。

## Q3 · 【必刷】多高调用量才值得自建 GPU？算笔账。
**骨架**：先过两道硬门(隐私一票否决 / 要不要最强闭源模型)再算钱。自建=固定成本(GPU 折旧+电+运维)、云=变动成本(按 token)，拐点=月 token 量×云单价 vs GPU 月成本+运维摊销。数量级：24GB 卡约 1.5-2 万/3 年摊 ~500/月 + 电托管一两千/月，通常要日均百万 token 级且长期稳定才划算。**低/波动流量 GPU 大量空转、单位成本远超云**，利用率<30-40% 几乎一定用云。诚实：排产自建主因是**数据不出域硬约束不是成本更优**。

## Q4 · 【补充】campaign 里 Semaphore 和 brake.signal 不重复吗？PolicyGate 一把全局锁不瓶颈？
**骨架**：两个正交层。Semaphore=进程内、硬、零延迟并发上限(护共享资源，默认 1 退化串行)；brake.signal=跨 agent、软、有传播延迟的协同降速(某 agent 熔断后广播、同链路停派活防雪崩)。**Semaphore 无法表达"下游坏了"，brake 补这个语义**；软背压有延迟窗口故必须软硬叠加。锁不瓶颈：锁里只包"读预算→判断→扣预算"微秒级内存操作，LLM 调用在锁外并行；**预算串了是真超支烧钱，比吞吐损失严重**，故意选强一致。变重(查远程 DB)就换分片锁或 CAS。

## Q5 · 【补充】前缀缓存怎么保证真命中？有哪些坑让它形同虚设？
**骨架**：前提=前缀逐字节相同、失效级联(前面变后面全废)。最稳定放最前(tools→system→历史)。坑①system 塞易变字段(时间戳/随机 id)让前缀永不命中→挪到靠后。坑②上下文压缩/丢历史和缓存打架(省的 token vs 重算缓存的 token)，按压缩频率+缓存 TTL 联调(vLLM APC 无 TTL 靠 LRU、Anthropic ephemeral 默认 5min)。坑③并发首批互不命中(要等第一个返回才建立)。nanocodex 已读 `prompt_cache_hit/miss_tokens` 实测命中率。机制层 vLLM 靠 PagedAttention+continuous batching。

## ★备弹（服务架构，被深挖时）
- **runtime 怎么挡漏网的模态？**→ 硬过滤不只选型期，runtime 落成**输入 guard**(MIME/魔数嗅探、非文本占比检测)，不匹配 Cap_in 直接拒/路由降级链，同 privacy-gateway 密钥硬 block 一类前置布尔闸门。
- **分段路由段间错误传播怎么归因？**→ 配端到端 trace，每段打独立 span(输入指纹/模型档/耗时/置信度)，段级归因(NCX_TRACE)；段间设质量闸(ASR 置信度低标降级/触发复核)。这是全能模型省掉的运维成本。
- **熔断半开放几个探针？多个上游同时恢复会二次打垮吗？**→ 半开只放极少探针(1 个或个位数)串行/限并发，成功才逐步放量；恢复要 jitter/渐进防惊群(同"别让一批请求同时醒来")，brake release 要渐进放量/错峰。
- **fallback/多 key/重试叠加会重复副作用/双花吗？**→ 超时≠没执行，主可能已扣费你却切备=双花。有写副作用/计费的必须带 **idempotency-key** 去重或本地指纹表；纯只读推理才可放心 fallback。同 PolicyGate 用锁把扣预算包临界区。
- **三维决策表会规则冲突吗？怎么灰度/回滚？**→ 决策表当**配置非硬编码**：集中式规则表+单测覆盖每 cell(高敏感必命中 local 做断言)+变更走灰度(shadow→按比例)+一键回退+**fail-safe 默认落最保守格(高敏感+拒绝)**。
- **27B 冷启动几十秒~分钟，突发峰值等得起？**→ 大模型副本冷启动=权重加载+引擎预热，秒~分钟级，无法秒级弹起。策略偏"保底常驻+预热池"，峰值靠排队+限流+背压顶住或溢出到云 burst。弹性差本身是成本。
- **可观测盯哪几个黄金信号？SLO 怎么定？**→ 分层：请求层 RED(Duration 看 p95/p99 且分 TTFT/整体)、降级层(降级率/fallback 命中/熔断开合)、成本层(token/prompt_cache_hit)、限流层(429/Retry-After/Semaphore 排队)。SLO 建业务可感知指标(有输出率/p95)，告警建 error budget burn rate 非单点抖动。
- **单进程 Semaphore 多副本部署配额被×4 打爆？**→ 多副本必须把配额上提共享层：Redis 令牌桶+Lua 保证原子(同 PolicyGate 扣预算)，或静态分片(简单但利用率低)。副本固定用分片、弹性用共享桶。这也解释 campaign 单进程 asyncio.Lock 够用、分布式就得换 Redis Lua。
- **continuous batching 会拖慢单请求 TTFT 吗？**→ 会，吞吐和单请求延迟是一对权衡。调 max_num_seqs/gpu_memory_utilization/chunked prefill 找点：交互式压低 batch 保延迟、批处理放大 batch 保吞吐。配套"交互式高优/批量低优"分层，最好走不同副本池。
