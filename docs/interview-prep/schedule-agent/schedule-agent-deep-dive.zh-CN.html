① 四段治理（写操作流水线）★

机制

写请求的真实流经是分支图不是直线（graph/graph.py 实测）：

START → rewrite → route ─┬─ need_clarify ─→ respond        (歧义/confidence<0.5/缺实体)
                         ├─ readonly ─→ query → rag → answer_verify → respond
                         └─ write ─→ governance ─┬─ blocked ─→ respond
                                                 └─ approved → preview ─┬─ await_confirm → respond
                                                                        └─ execute → execute → verify → respond → END

四段 = governance(权限/风险) → preview(dry-run 只读) → execute(落库) → verify(回读+审计)。写操作永远先过前三关，execute 前必须 confirmed。

关键代码

三条件边（graph/conditions.py，逐字）：
· after_route：intent_ambiguous / confidence<0.5 / missing_entities 任一 → need_clarify；is_write → write；else readonly。
· after_governance：not governance_passed → blocked；else approved。
· after_preview：confirmed is True → execute；else await_confirm（严格 is True，不是 truthy）。
preview（graph/nodes/preview.py）：按 intent 分派 8 个 _preview_* 函数，每个只 query 不写，返回 {action, summary, …, impact:[…]}；不设 confirmed —— confirmed 由外部（人工审批入口）注入，这是 HITL 落点。

数字/常量

10 节点 · 3 条件边 · 8 个 intent 有 preview 处理器 · execute→verify 是普通边（执行后必回读）。

诚实边界

· verify 不回滚（见 ③）——不一致只标 needs_review。
· 单实例；confirmed 注入是入口的事，图内不管。
· 未实现 preview 的 intent 落 {"summary":"…（待实现）"} 兜底。

被追问链

为什么写操作要拆四段，不直接执行？
把"判断→预览→执行→验证"拆成四道确定性门，人只在 preview→execute 之间注入 confirmed（HITL）。安全建在图结构上，不靠模型自觉——模型跑偏也越不过图的边。
confirmed 谁设的？为什么用 is True 不是 truthy？
preview 节点不设 confirmed，由人工审批入口注入 True。用 is True 而非 truthy 判断，是防 "1"/"yes"/非空对象这类 truthy 值误判成"已确认"——只有布尔 True 才落库，写操作的保守。
readonly 和 write 怎么分流？
after_route 看 is_write（intent 是否属 WRITE_INTENTS）；但先判 need_clarify（歧义/confidence<0.5/缺实体）——不确定就不往下走，宁可追问。
为什么 governance 在 preview 之前？
先权限后预览：没权限的连预览都不给看（避免泄露订单/机台数据），权限是第一道门。preview 只对已授权的操作算影响。
preview 崩了会拖垮整条链吗？
不会。preview_node 里 try/except 包住，异常返回 {"error":"preview_failed","message":…}，图继续走；后续 verify 看 tool_result.success 判定。

② 权限 + DryRun ★

机制

governance_node 做两件事：①角色层级权限检查 ②高风险操作的实体兜底。查询灵活（只读不过 governance），写操作保守（必过）。DryRun（preview）是执行前"看清影响再决定"的只读关。

关键代码 graph/nodes/governance.py

· ROLE_HIERARCHY = ["业务员","工艺员","主任","厂长"]（index 0–3）；_get_role_level 返回 index，未知角色 → -1（最低）。
· 权限判定：minimum_role = intent_config["minimum_role"]（来自 intents.json）；user_level < required_level → blocked。
· 风险检查：risk_level=="high" 时，machine_failure 缺 machine_id → blocked（reason_code=missing_machine_id）。
· need_approval = intent_config["need_approval"] —— 是否走人工审批也是 config 驱动。
· blocked 立即 log_audit(status="blocked") 并返回 governance_passed=False。

数字/常量

4 级角色（0/1/2/3，未知 -1）· 3 个 blocked reason_code：unknown_intent / permission_denied / missing_machine_id。

诚实边界

· 权限是每意图静态 minimum_role，不是数据级 ACL（"某人只能改自己的订单"这种没做）。
· 风险检查目前只硬编码了 machine_failure 一条，其他高危靠 route 追问兜。
· DryRun 的影响估算是"查库预估"，不是真事务模拟。

被追问链

权限到底怎么判的？给不给模型？
角色查 ROLE_HIERARCHY 得 level，和 intent 的 minimum_role 比，低于就 blocked。全确定性、不给模型——安全相关分类（权限/是否可写/风险）绝不交给模型（信条）。
未知角色、未知意图怎么办？
fail-closed：未知角色 level=-1 恒最低权限；未知意图直接 blocked（reason_code=unknown_intent）。不认识的一律不放行。
DryRun 和普通"预览一下"有啥区别？
它是写操作前强制的一道只读关，产出 impact 清单（会动哪些订单/机台/日期），确认后才 execute——不是可选的 UI 预览，是安全防线。
高危操作怎么防？
分级（risk_level）+ 缺关键实体直接 block（machine_failure 无 machine_id）+ need_approval 走审批。物理拦截，不靠 prompt 劝模型别乱来。
接手的，如果让你重新设计权限？
上数据级 ACL（行级：谁能改哪些订单/机台），把 risk_level 硬编码检查改成可配置规则表，再叠操作频率限流。现在够用但粒度粗，这是诚实的改进方向。

③ 审计 audit_log ★

机制

写操作全程留痕、append-only。governance 拦截时写一条，verify 执行后写一条；execute 本身不写——审计落在"决策点(governance)"和"验证点(verify)"，不在"动作点(execute)"。

关键代码 tools/audit_log.py

真实 schema（17 列）：id, trace_id, created_at, intent, action, actor_role, request, target_order_id, target_machine_id, status, success, need_approval, error, before_state_json, after_state_json, verify_checks_json, metadata_json。
6 个索引：trace_id / created_at / intent / status / target_order_id / target_machine_id（查得快）。
· log_audit() 自动从 entities/after_state 抽 target_order_id/target_machine_id 建索引列。
· 写点：governance.py 3 处（unknown_intent / permission_denied / missing_machine_id，status=blocked）+ verify.py 2 处（执行失败 status=failed/skipped；回读后 status=passed/needs_review）。
· before_state=preview_result（改前预估），after_state=tool_result（改后实况）。
· 查询：recent_audit_rows(limit=50) 反序列化 json 列；按 trace_id 索引查单链路。

数字/常量

17 列 / 6 索引 · success、need_approval 是 INTEGER(0/1)。

诚实边界

· execute 不写审计——execute 若崩在 verify 之前，靠 verify 记 failed 兜（但没有"execute 已发起"的独立时点）。
· 审计与业务同库（SQLite），无独立审计库/WORM，防篡改级别有限。
· created_at 用 time.strftime 本地时间，非 UTC/单调时钟。

被追问链

为什么只在 governance 和 verify 写，execute 不写？
审计记的是"决策和结果"不是"动作过程"：governance 记"为什么拦/放"，verify 记"改完回读对不对"。execute 只是执行，其结果由 verify 回读后如实入账（before=preview，after=tool_result）——记结果比记动作更有追责价值。
success 到底怎么判？
success = tool_result.success AND all_passed（verify 回读的 checks 全过）。光执行成功不算，回读还得一致；不一致 → success=0 + status=needs_review。
能复原整条链路吗？
能。trace_id 有索引，一次请求的所有 audit 行按 trace_id 拉齐；before/after_state 还原改前改后状态。管理台 recent_audit_rows() 直接看最近 50 条。
append-only 怎么保证？会被改吗？
应用层只 INSERT、不 UPDATE/DELETE。但同库无 DB 级 WORM——真要防篡改得独立审计库 + 哈希链/外部只追加存储。这是诚实缺口。
审计能看出"批准的 vs 实际执行的"不一致吗？
能。before_state(preview 预估) 对 after_state(tool_result 实况) 直接比对——这也正是 verify 判 needs_review 的依据。批的是 A、执行成 B，审计里一眼看出。

⑤ 意图打分（零 LLM）★

机制

意图识别纯规则/关键词打分，零 LLM。score_intents 遍历 intents.json 每个意图算分→排序→top1 为结果；_score_to_confidence 把分数阶梯映射成 confidence；analyze_intent_ambiguity 判歧义。

关键代码 graph/nodes/route.py

· _calculate_intent_score：命中 trigger_phrases +12、各意图关键词 +16~40、冲突信号 −30~−40；特判 _looks_like_rule_question → ask_rule 直接 score=999/conf=0.95。
· _score_to_confidence：score≥30→0.95 / ≥24→0.90 / …；无分 → unknown, 0.2。
· analyze_intent_ambiguity：top1/top2 分差 ≤ AMBIGUOUS_MARGIN → 歧义；is_write 且 confidence < WRITE_CONFIRM_CONFIDENCE → 歧义（写操作低置信不猜）。
· classify_intent(text) → (intent_code, confidence)；route_node 产出 intent_code/confidence/intent_candidates[:3]/is_write/missing_entities。

数字/常量

加分 +12 / +16~40，扣分 −30~−40；conf 阶梯 30→0.95、24→0.90；unknown=0.2；ask_rule 特判 999。

诚实边界

· 纯词法，漏长尾/口语化/同义变体；关键词权重是手调 magic numbers（靠 audit self_recognition + golden 覆盖兜）。
· 优化：规则低置信才调大模型前置兜底 + embedding 语义匹配 + 未命中样本聚类挖新意图。

被追问链

意图识别为什么零 LLM？confidence 哪来的？
意图决定路由和权限，是安全相关分类，不能交给概率模型——用规则打分：确定性、可复现、零成本。confidence 是 _score_to_confidence 把规则分数阶梯映射来的，不是模型概率。（这题最容易被抓自相矛盾，务必答"规则"。）
意图类型超十个，怎么扩展不出乱子？
config-driven（intents.json 加一条=加配置不改核心）+ audit 5 检查防退化（dark/conflict/self_recog/coverage/orphan）——加了不抢老意图命中、有 golden 覆盖、不产生孤儿。
纯关键词漏召回怎么办？
现状靠 trigger_phrases + 关键词加权，长尾会漏；优化是低置信才调大模型兜底（省成本）+ embedding 语义匹配，对未命中样本聚类挖新意图回流 intents.json。
写操作意图识别错了、直接执行了怎么办？
识别错也越不过四段治理：低置信/歧义 → need_clarify 追问；写操作还要过 governance 权限 + preview 确认。意图只是入口，安全靠图结构不靠意图准。

⑥ RAG / 检索（按场景路由）★

机制

不是一条链打所有问题，而是按意图路由到不同 retriever（INTENT_RETRIEVER_MAP）。query_plan 先判该不该检索；grounding 做在模型外（state 里的 grounding_contract / answer_verification / retrieval_steps）。

关键代码 rag/retrievers.py

· 意图→retriever 映射：ask_order_status/ask_machine_load→sql，ask_rule→hybrid，ask_reason→composite，query_failure_impact→graph，默认 hybrid。
· SQLRetriever：order_id/machine_id 直接 SQL（ctsalebid/jt/gg/pcrq/ddsl），score=1.0（精确最高）。
· VectorRetriever：fastembed bge-small-zh-v1.5 512 维 + Qdrant（32 条规则）；不可用返回 []。
· HybridRetriever：向量召回 top_k×3 候选 → 关键词重排（每命中 +0.1）→ 取 top_k；向量挂了全靠关键词。
· GraphRetriever：networkx 3 跳（machine→order→spec→alt_machine），答故障影响。
· route_and_search：主 retriever 空 → 降级 file_keyword；统一返回 [{source,title,text,score,metadata}]，失败返回 [] 不抛。
· grounding 字段（graph/state.py）：query_plan / retrieval_steps(防无限检索) / grounding_contract(允许来源) / answer_verification(回答前证据校验)。

数字/常量

bge-small-zh-v1.5 512 维 · Qdrant 32 条规则 · Hybrid 候选池 top_k×3、关键词 +0.1/命中 · 实测 Recall@3=0.83 / MRR=0.956。

诚实边界

· CaseRetriever 目前是 stub（复用 vector + 标记 case，audit_log 向量化未实现）。
· GraphRAG 是 networkx L1，不是 Neo4j。
· Vector 依赖外部 Qdrant 路径（D:\schedule-agent-foundry\data\qdrant_local），不在就返回 [] 全靠 file_keyword。
· Rerank 生产不默认开（小规则库易被标题权重带偏，1000+ 条再引入）；Neg-Precision=0% 是 BM25 短板。

被追问链

为什么不纯向量一把梭？
订单号/机台/规格是强约束字段，纯向量把"语义相似"误当"业务正确"。所以精确走 SQL(score=1.0)、规则走 Hybrid(向量+关键词重排)、诊断走 Composite、故障影响走 Graph。
怎么防 RAG 幻觉 / 订单不存在还编机台？
grounding 做在模型外：grounding_contract(限定允许来源) + answer_verification(回答前证据校验) + retrieval_steps(防无限检索) + response_must_not_contain(不存在禁编字段)。模型只能用喂进来的证据。
GraphRAG 这种为什么不能用向量？
"机台故障影响哪些订单"的答案不在任何一段文字里，是顺着 machine→order→spec→alt_machine 3 跳关系拼出来的。向量检索文本片段无能为力，得走图。用 networkx 抽 SQLite 成图（L1，不上 Neo4j）。
retriever 挂了/Qdrant 不可用怎么办？
每个 retriever 失败返回 [] 不抛异常；route_and_search 主 retriever 空就降级 file_keyword（本地 md 关键词，永远可用）。RAG 挂了系统还能答，只是质量降级。
诚实说，哪些是没做完的？
CaseRetriever 是 stub（复用 vector，真实现要 audit_log 向量化 + 90 天时间过滤）；GraphRAG 是 networkx L1 玩具级；Rerank 没生产化。规则库到 1000+ 条这些才值得补。

⑦ 可观测 / Tracing

机制

每请求一个 trace_id，节点级 Span 记录；用 P95 而非 avg 看尾延迟；节点级 P95 定位慢节点；异常检测三类。

关键代码/结构 interview_challenges/solutions/solution_08.py

· 三层模型：Span(name/trace_id/start·end/status[OK·ERROR·TIMEOUT]/attributes/error) → Trace(spans[]/is_success=all OK) → MetricsCollector/AnomalyDetector。
· 异常检测三类：延迟(节点历史 P95×2) / 错误率(最近 window 错误率≥阈值) / 成本(单请求超预算)。
· 生产另有 eval/tracer.py 接 Langfuse/LangSmith（graph.compile 时按环境变量注入 callbacks）。

数字/常量（实测 solution_08）

端到端 P50=941 / P95=4702 / avg=1480ms；节点级 LLM P95=4588 vs Route P95=15ms；成功率 90%；50 请求 ¥0.0774；7 个慢请求 >2000ms。

诚实边界

· 延迟基线用了含异常样本的全量数据→自指污染，生产要滑动基线（排除近期窗口）。
· 扁平 span，无 OTel 父子树。
· ⚠️ 这 4702ms 是含 LLM 的端到端；别和 eval 规则检查 28ms 混（那个不打模型）。

被追问链

为什么 P95 不用 avg？怎么定位慢节点？
avg 掩盖长尾，P95 反映尾延迟=体感命门。定位靠节点级 P95：LLM 4588ms vs Route 15ms，一眼看出锅在 LLM 不在路由。复现 python -X utf8 …/solution_08.py。
异常检测怎么做的？基线哪来的？
三类：节点延迟超历史 P95×2、window 错误率超阈值、单请求超预算。诚实坑：基线用了含异常样本的全量→自指污染，生产要滑动基线（排除刚发生的异常窗口）。
为什么你 eval 2 秒跑完但生产 P95 4.7 秒？
两个不同东西：eval 规则检查不打模型（P95=28ms），生产端到端要等 LLM（P95=4702ms，其中 LLM 占 4588ms）。规则回归快正是因为它测的是确定性管线逻辑，不是模型延迟。

⑧ 多轮记忆 / 指代消解

机制

rewrite_node 前置：规则先判"需不需要重写" → 需要才调 LLM 用最近 3 轮历史改写成"自包含 query" → LLM 失败降级规则拼接。70%+ 单轮自包含直接直通、零成本。指代消解靠"改写"，不靠向量召回。

关键代码 graph/nodes/rewrite.py

· need_rewrite 3 信号：①有指代词(那/这/它…)且无实体 ②超短追问(<8 字且在 SHORT_FOLLOWUPS) ③短 query(<12 字)+无实体+有历史。首轮绝不重写。
· _has_entity：订单号/规格/机台号正则——有具体实体就当自包含，不重写。
· _llm_rewrite：DeepSeek(temperature=0)，喂 _format_history(max_turns=3)，输出一行自包含 query，失败→None。
· _rule_rewrite(无 LLM 降级)：从历史正则抽最近机台号/订单号/规格，拼到当前 query 前。
· state：original_request(不动，审计/Langfuse 用) + rewrite_applied。

数字/常量

最近 3 轮历史(max_turns=3)；超短追问 <8 字、短 query <12 字；DeepSeek temperature=0。

诚实边界

· 无 DEEPSEEK_API_KEY → 规则拼接(demo 级，"生产建议配 LLM")。
· 需重写判定是规则启发式，可能误判（漏判指代/误判自包含）。
· 结构化多轮状态(订单/机台/确认态)走 State 字段，不进向量库。

被追问链

"把它排到 101" 怎么知道"它"是谁？
rewrite_node 检测到指代词"它"且无实体 → 调 LLM 用最近 3 轮历史改写成"把订单 SO-X 排到 101 机台" → 再进 route。LLM 挂了就规则拼接（抽历史最近订单号）。
为什么不用向量召回做指代消解？
向量会把"语义像但时间无关"的历史块拉进来误导。指代要的是时序最近（刚才说的那个订单），不是语义最相似——所以用最近 N 轮原文 + 改写，不用 RAG。
每轮都调 LLM 重写不费钱吗？
不。规则前置过滤：70%+ query 自包含（"101 机台坏了影响哪些订单"），直接直通零成本；只有命中 3 个信号的多轮 query 才调 LLM，省 200–500ms + token。
重写错了怎么办？
多重兜底：LLM 失败→规则拼接；重写后==原文→标 rewrite_applied=False 走原 query；original_request 永远留底可审计。且重写只影响检索/路由，写操作还有四段治理兜。

✅ 8 个承重点全部抗打（写链路 3 + 意图 + RAG + 可观测 + 多轮记忆；评测独立成篇 eval-deep-dive）。全部锚真实代码。这份 = 被钻到 L3 时的兜底层。
