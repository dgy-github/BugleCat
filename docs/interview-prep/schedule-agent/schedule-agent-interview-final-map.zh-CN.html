① 定位 1.0最小可行闭环·接手改造
49981 订单 · 19 类写意图

叙事：已上线制造业排产 1.0 最小可行闭环——不覆盖全量工厂规则，但验证了 Agent 做自然语言理解→规则匹配→流程编排→DryRun→结果解释的可行性。

L3：49981 条真实订单、19 类写意图、systemd 部署+公网隧道；半途接手，原排程算法非自研。

被追问：为什么叫"最小可行"→规则不全量、无 solver 优化，但写操作全链路治理已闭环、已上线。

② 为什么用 Agent 多角色多约束动态调度

叙事：排产不是单点查询，是多角色、多步骤、多约束的调度系统，需求动态（急单/临时调整/参数不全/表达不标准）。规则做确定性判断，Agent 做编排+人机交互，模型做语义理解+解释。

被追问：哪些给模型→判断/分类一律不给。安全分类(权限/是否可写/风险)不给；意图识别本身也不给——规则+关键词打分(_calculate_intent_score 遍历 intents.json，零 LLM)，confidence 由 _score_to_confidence 把规则分数阶梯映射(≥30→0.95…)不是模型概率；消歧看 top1/top2 分差 或 写操作 confidence 不足→need_clarify。给模型的只有后置语义理解/解释/澄清。

③ 规则在前模型在后 确定性在前·模型后置增强
confidence<0.5 → need_clarify

叙事：核心判断(订单状态/机台负载/规格匹配/权限/能否停排/能否故障转移)走规则+SQL+确定性逻辑；模型只做后置增强(信息补充/格式优化/规则说明/澄清/解释)。

被追问：模型到底做什么→不做决策，做"翻译官"：理解需求、解释方案、补规则说明、参数缺失时澄清。

④ 四段治理 ★ 写操作永不直接落库
confirmed is True · needs_review 不回滚

叙事：写操作不让 Agent 直接执行，走 governance→preview→execute→verify 四段。

L3：真实拓扑 route→…→governance→preview→execute→verify→respond；after_governance 看布尔 governance_passed；after_preview 严格 confirmed is True 才 execute(人在回路)；preview 纯 dry-run 只读产 impact；verify 回读 checks[]，不一致不回滚→needs_review 标人工复核；故障转移批量改 LIMIT 50。信号串 is_write→governance_passed→confirmed→verify_result。

被追问：verify 不一致为什么不自动回滚→制造业写操作影响面复杂，自动回滚可能二次扰动，标复核转人工更稳。

⑤ 安全/权限/DryRun 4级角色·物理隔离
ROLE_HIERARCHY 0-3 · blocked 三因

叙事：DryRun 不是普通预览，是写操作前的安全防守层；查询灵活、写操作保守。

L3：角色层级在代码 ROLE_HIERARCHY=[业务员0,工艺员1,主任2,厂长3]，user_level<required→blocked(required 来自 intents.json)；blocked 三因：未知意图/权限不足/高危缺实体(机台故障缺 machine_id)；网关 /agent/approval/create→confirm/reject。

被追问：danger-full-access 全放吗→否，只清 escalation bit 不改 approval policy，untrusted 下未知命令仍 Ask。

⑥ 审计 append-only·可回链
只在 blocked/verify 写

L3：audit_log append-only，字段 trace_id/intent/action/actor_role/status/success/need_approval/before_state_json/after_state_json/verify_checks_json；只在 governance-blocked 和 verify 两处写，execute 本身不写；before=preview_result、after=tool_result 可比对"批准的 vs 执行的"；查询 /agent/audit/{trace_id}。

被追问：success 怎么判→verify 全过才 true，回读不一致降 false+needs_review。

⑦ RAG ★ 5 Retriever 分场景
Recall@3=0.83 · 切块 MRR=0.956

叙事：不是一条链打所有问题，按场景路由 5 种 Retriever；query_plan 先判该不该检索(structured_sql/rag)，写操作跳过 RAG。

L3：SQL(订单/机台精确)/Vector(规则语义)/Hybrid(规格颜色强约束,RRF)/Case(历史案例)/Composite(诊断=SQL+RAG)；防幻觉 answer_grounded+evidence_source=sqlite+response_must_not_contain+max_retrieval_steps。实测 Recall@3=0.83、markdown 切块 MRR=0.956(诚实短板:Neg-Precision=0%,BM25 不会说无匹配)。Rerank 生产不开(小规则库被标题权重带偏)。

被追问：为什么不纯向量→订单/机台/规格是强约束字段，纯向量把语义相似误当业务正确。

⑧ 可观测 ★ Span/Trace·节点级定位
P95=4702ms · LLM 4588 vs Route 15

叙事：每次请求一个 trace_id，节点级日志，出问题按 trace_id 还原链路定位是哪个节点。

L3：三层 Span(name/status[OK·ERROR·TIMEOUT]/attributes)→Trace(is_success)→Metrics/Anomaly；P95 不用 avg(avg 掩盖长尾)；节点级 P95 定位慢节点。实测端到端 P95=4702ms、LLM P95=4588 vs Route 15(锅在 LLM)、成功率 90%。诚实坑：延迟基线含异常样本自指污染，扁平 span 无 OTel 父子树。

被追问：给个数字/怎么定位慢节点→端到端 P95=4702 拆到节点级 LLM 4588 就知锅在 LLM。

⑨ 评估 ★ 三层防护+数据飞轮
44/11类 · rule_pass_rate≥1.0 · audit 5检查

叙事：不看单一准确率，自动指标定位链路问题 + 人工指标判断业务价值(人工指标拆细:对交期满意还是对机台推荐满意)。

L3：三层 audit(skill 健康 5检查 dark/conflict/self_recog/coverage/orphan)→check_expected(~16 类确定性断言)→judge(LLM 3维1-5可降级)；CI audit→rule-eval∥full-eval，门禁 rule_pass_rate≥1.0；数据飞轮 audit_log→mine_eval_candidates→人审→online_hard_cases→run_scheduled_eval。

被追问：judge 打不准→人工校准子集验 judge-human 一致率<0.9 不信，能转确定性断言的不用 judge。

⑩ 记忆/上下文 任务状态·指代·压缩
指代靠最近 N 轮原文，不靠 RAG

L3：维护多轮任务状态(订单号/机台/目标机台/规格/DryRun 结果/确认状态)；指代消解靠最近 N 轮原文不靠 RAG(时序邻近≠语义相似)；历史压缩=滑窗+摘要；结构化事实走 DB 不进向量库。

被追问："把它排到101"里"它"是谁→靠会话记忆最近 N 轮原文，不靠向量召回(会拉进语义像但时间无关的历史块误导)。

⑪ 驾驭工程 + 长期治理 难点是体系化建设

叙事：核心是驾驭大模型概率性输出，放进可执行/可观测/可评估/可测试系统。控制手段:结构化输出、关键参数过规则校验、写操作五段、低置信澄清不猜。1.0 借 AI 做得快，真难的是长期治理:规则沉淀/边界 case 收集/人工标注/评估集扩展/线上回流/多角色协作，周期长。

被追问：后续难点→不是换模型，是体系化建设 + 开发/PM/生产主管/工艺/业务多方协作。

🔥 硬追问补充（面试常钻·点开看骨架）

意图识别怎么扩展 19 类，超 10 个
config-driven + audit 防退化

L3：意图 config-driven——intents.json 每条 = code/category/trigger_phrases/required_entities/risk_level/minimum_role/need_approval/steps；加意图=加一条 config，不改代码；route 规则+关键词打分(零 LLM)识别。

防扩展后退化：加意图必跑 skill audit 5 检查——dark(某意图所有 trigger 命中不到自己)/conflict(一短语被多意图声明→路由不稳)/self_recog<0.5/coverage(golden 没覆盖)/orphan(route 引用了但 intents.json 没定义)。配套加 golden case + 权限层级 + 治理分派。

被追问：意图多了路由冲突→conflict 检查 + confidence 门控 + 歧义判定(top1/top2 分差小→need_clarify)。

并发怎么处理 同订单/系统压力
读写分离 + 订单级 trace 写锁

实际做法（读写分离 + 订单级锁，真做了）：①路由前查询阶段加锁；②意图澄清后判是不是写操作——读操作直接放过(不锁)；③写操作先查该订单当前有没有 trace_id 日志在写；④若有在写 → 返回"有其他人正在操作该订单，请稍后重试"。本质=用 audit/trace 日志做订单级悲观写锁：读多不锁、只锁同订单的写、不同订单不互斥。

系统压力：令牌桶限流 + 队列削峰 + 本地模型 Semaphore 并发上限。

被追问(这个锁的坑=优化方向)：①check"有没有在写"和"标记我在写"要原子，否则 TOCTOU(两请求同时检查都发现没锁)——单实例 asyncio 临界区内安全，跨实例要 DB 唯一约束/Redis SETNX；②写崩溃/超时要TTL/超时释放否则订单锁死；③多实例要把锁放共享存储；④叠幂等键防重试双写。

Token / 内存成本管理 本地模型
成本=算力，上下文靠结构化状态压

L3：排产用本地 Qwen，成本是算力不是 API $，但仍要管上下文膨胀。手段：任务级摘要 + 结构化状态压缩(只留订单号/机台/DryRun结果/确认态，不留全对话)；query_plan 减无谓 RAG(结构化直查省 token)；读过的结果摘要化存 ID 复用不重读。

显存：Qwen 27B GGUF Q4 量化压显存 + KV/前缀缓存。

被追问：上下文爆了→滑窗+任务摘要，结构化状态而非全文(同 nanocodex 非破坏压缩思路)。

怎么保证 RAG 准确性 ★
该不该查 + 有据才答

四道：①query_plan 判该不该检索(结构化直查不走 RAG) ②hybrid(BM25 精确+dense 语义) ③grounding 校验做在模型外(answer_grounded+evidence_source=sqlite+response_must_not_contain 禁编字段) ④eval 量化(Recall@3=0.83)。

被追问：准确性不靠"更强 embedding"，靠"该不该查的路由 + 有据才答的 grounding + verify 回读"——强约束字段走 SQL 不走向量。

RAG 有哪些扩展空间 可操作
分层加，不堆技术

扩展空间：Rerank(规则库 1000+条再开) · query 改写/HyDE/子问题拆解 · 父子块(检索粒度≠喂 LLM 粒度) · Graph RAG(诊断多跳关系) · 增量 upsert/蓝绿重建索引 · chunking 策略优化 · 评测集扩充 · 垂域词 embedding 微调。

被追问：怎么扩→按"先判该不该查→检索优化(hybrid/chunking/metadata)→重排→Agentic/Graph"分层加，不是一股脑堆。

为什么用 LangGraph ★ 不只是编排
低层有状态编排，五个真价值

纠正框架：LangGraph 不只是节点/工作流编排，是低层有状态编排框架，五个真价值：①状态管理(ScheduleState 跨节点流转) ②持久化/durable execution(checkpointer 保存每个 super-step，崩溃从断点恢复) ③human-in-the-loop(interrupt/checkpoint——排产 confirmed 确认就靠它) ④cycles/条件边(不只 DAG，支持环) ⑤time-travel(checkpoint 历史回放调试)。+ streaming / subgraph / Store(长期跨线程记忆)。

排产为什么选它：写操作要"固定流程+每边界插治理+可恢复+可 HITL+每节点可测+trace 定位"——正是它的强项；LangChain 的 chain 抽象藏控制流做不到，Pydantic-AI 强在类型不强在图编排。

LangGraph 最新版本新特性 1.0
durable execution · node cache · deferred nodes

LangGraph 1.0(生产版，Uber/LinkedIn/Klarna 在用)：durable execution(崩溃自动从断点恢复)；checkpointer 多后端(InMemory/Postgres/SQLite/DynamoDB+S3 存大 payload)；Store(长期跨线程记忆，区别于 checkpointer 的线程内)；node caching(CachePolicy(ttl=…) 缓存节点结果省重复计算)；deferred nodes(等所有上游完成才执行，做 map-reduce/consensus)；prebuilt ReAct 的 pre/post model hooks(pre 压缩历史控上下文、post 加 guardrail/HITL)。

诚实：有分析(Diagrid，竞品)认为 checkpoint≠完整 durable execution(要开发者自己检测/触发/协调)，权衡看来源。

🚀 优化方向（被问"怎么优化/下一步"时·点开看现状→优化）

答法：现状能用 + 有 X 局限 + 优化方向 Y + 当前不做因为 Z(优先级/成本/数据量)。"知道怎么优化但选择不做"＞"没想过"。

🔄 下一步：Bad-case 回流飞轮
提取→分类→人标→新 Case

4 步：①线上可观测日志提取 Bad Request → 抽成待评估用例；②分类：响应请求异常 vs 业务理解异常；③业务理解异常由业务人员人工标注 → 确定下一轮需求；④深化成新 Case(新评测数据)回流 golden。

关键洞察(分类=路由键+省成本)：响应异常自动分类走工程线(超时/500/schema失败/工具error/needs_review 是确定性信号，不麻烦业务)→修代码/重试/降级；业务理解异常才送人标(系统自认为成功但业务判错，靠人审改判率/低置信/用户反馈捞)。只把语义异常送人标=省标注成本(确定性优先)。

再分一层(标注时)：业务理解异常里区分 模型理解错(prompt/意图/抽取→工程修) vs 规则缺失/过时(需求变更→业务定，才进"下一轮需求")。

落到真实代码：audit_log 带 reason_codes → mine_eval_candidates 挖候选 → eval_candidate_case 表 → review_eval_candidates 人审 → 晋级 online_hard_cases.json(source: audit_id/trace_id/reason_codes) → run_scheduled_eval(min_pass_rate=1.0)。

被追问：①怎么自动分响应vs业务异常→响应异常有确定性信号可自动，业务异常难自动发现靠改判率/低置信捞；②标注成本/不一致→rubric+双标一致性+只标高价值(高频/边界)；③新 case 会不会过拟合评测→加 case 过 audit(coverage/conflict)+留 held-out+online 单独集；④只收 bad case 评测集越来越偏→bad case + 正常分布采样保代表性。

🏭 调度优化能力（1.0 最大缺口）
现无 solver → 接排程引擎/规则最优化

现状：规则匹配 + SQL 查询 + 就近/负载启发式，没有真正的组合优化 solver。

优化：接真实排程后端 API / OR-Tools 类 solver 做最优化(交期×产能×换型最小化)，LLM 退成 NL→约束 的翻译官(呼应合规-vs-排产的理想版)。这是 1.0→2.0 最大方向，也是最诚实的"未做"。

🎯 意图识别
规则零LLM → 大模型前置兜底

现状/局限：规则+关键词打分(零成本、可复现)，但漏召回模糊/长尾/口语化。

优化：规则低置信时才调大模型前置兜底(省成本)+embedding 语义意图匹配+对未命中样本做意图聚类挖新意图回流。

⚙️ 并发
订单级trace锁 → 原子化+TTL+多实例共享

现状（已做）：读写分离 + 订单级 trace 写锁(写前查该订单有无在写 trace，有则拒并提示重试)。

优化：check-and-set 原子化(DB 唯一约束/Redis SETNX 防 TOCTOU) + 锁 TTL/超时释放(防崩溃锁死) + 多实例锁移到共享存储(Redis/DB) + 叠幂等键防重试双写；系统压力叠令牌桶限流+队列削峰。

💰 Token/成本
结构化状态 → 非破坏压缩+缓存+分层

现状：任务摘要+结构化状态压上下文；本地 Qwen 成本=算力。

优化：非破坏发送时压缩(借 nanocodex)+prompt/前缀缓存复用+fast/pro 分层(简单意图小模型)+显存 Q4 量化。

🛡 四段治理
verify不回滚 → 真事务+precondition

现状/局限：verify 不一致只标 needs_review 不回滚；confirmed 靠外部注入；simple 无 verify。

优化：写操作上真事务/checkpoint 回滚；execute 前加 precondition check(前提是否还成立)；verify 多输出"该重试 vs 该重规划"信号;给 simple 路径挂抽样复核。

🔎 RAG 准确性
Recall@3=0.83 → rerank+父子块+Graph

现状：hybrid+grounding，Recall@3=0.83；Rerank 生产未开、扁平块。

优化：规则库 1000+条开 Rerank；长条款上父子块(检索小块喂父块)；诊断类上 Graph RAG 多跳；垂域词 embedding 微调；golden 持续扩充。

👁 可观测
扁平span+自指基线 → OTel树+滑动基线

现状/局限：扁平 span 无父子树；延迟基线含异常样本自指污染。

优化：升 OTel 父子树(捕获嵌套工具/子调用)；异常检测用滑动基线(排除近期窗口)；告警建在 SLO error budget burn rate 不是单点抖动。

📊 评估
golden+judge → 线上信号反哺+held-out

现状：三层防护+数据飞轮，golden 44/11类。

优化：judge 校准集扩充验一致率；用线上信号(人审改判率)反哺离线维度权重(修 offline-online gap)；补端到端多轮回放；留 held-out 防选型/prompt 过拟合 eval 集。
