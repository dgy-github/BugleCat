🏭 排产 Agent · 全景梳理

在已有生产排程系统上加一层智能 Agent —— 不让 LLM 控业务，用确定性 workflow 编排，只在必要节点用模型。纺织/化纤行业，49,981 条真实订单，已部署(systemd+公网隧道)。

① 业务需求

目标：让工厂计划员用自然语言驱动排程系统，既能查、也能改，但改必须受控可审。

谁用工厂计划员，四级角色：业务员(0) < 工艺员(1) < 主任(2) < 厂长(3)
只读查询某订单排到哪了 / 某机台排了多少单 / 300D·红色300D 能排哪些机台 / 为什么某订单排不下(诊断)
写操作(19类)插单 / 暂停订单 / 切机台 / 改数量 / 故障转移(机台故障) / 改优先级 / 废弃 / 重算日期…
核心诉求①自然语言接入(降低使用门槛) ②写操作可控(权限+预览+验证) ③结果可解释可追溯 ④敏感数据不出厂
刻意不做不让 LLM 随意控制业务——排程逻辑确定、风险边界明确，用 LangGraph 固定流程，模型只在意图理解/规则检索/回复生成用

② 落地闭环

从自然语言请求 → 分流 → (读/写路径) → 结构化回复 → 线上失败回流金标，形成可持续改进的闭环。

③ 执行链路细节

真实节点顺序：rewrite → route → query → rag → answer_verify → governance → preview → execute → verify → respond。条件边 3 处，信号字段串起写链。

条件边判定
after_route歧义/`confidence<0.5`/缺实体 → need_clarify；`is_write`(WRITE_INTENTS) → write；else readonly
after_governance看单个布尔 `governance_passed`：false→blocked→respond；true→preview
after_preview严格 `confirmed is True` → execute；否则 await_confirm → respond(等人确认)
写链信号字段串：is_write(进写路径) → governance_passed(过闸) → confirmed(放行 execute) → verify_result.status(passed/needs_review)。每个节点输入输出可单测、可 trace，出错能定位到具体节点。

④ 技术细节

技术栈

  • 编排 LangGraph StateGraph
  • Python 3.12 · UI Streamlit 多页
  • 数据 SQLite(49,981 orders)
  • RAG Qdrant + fastembed bge-small-zh-v1.5
  • LLM 本地 Qwen3.6 27B(OpenAI 兼容)
  • Tracing Langfuse/LangSmith · 评测 Pytest+Golden+E2E

数据库 orders(纺织/化纤)

  • ctsalebid 销售订单编号(业务主键，Agent 定位用)
  • jt 机台 · gg 规格(旦尼尔如 545dtex/72f)
  • pcrq 排产日期 · ddsl 数量(吨) · scts 耗时
  • 日期 TEXT(ISO)可直接串比较；`status`/`jt` 多为 NULL(历史未回填/未分配)

5 种 Retriever(分场景路由)

  • SQLRetriever 订单/机台/规格历史 → 精确快
  • VectorRetriever 规则语义 → Qdrant
  • HybridRetriever 规格/颜色强约束 → 向量+关键词
  • CaseRetriever 历史排产案例(可解释)
  • CompositeRetriever "为什么排不下"→ SQL+RAG

部署(已上线)

  • systemd：Qwen 27B(8005)/bge(8007)/router(8008)/gateway(3010)/Streamlit(8501)
  • 公网隧道 → 5000 入口
  • Rerank 做过实验，生产暂不默认开(小规则库易被标题权重带偏，1000+条再引入)

⑥ 业务人员干预(HITL)

三个介入点

  • 预览确认：`after_preview` 严格 `confirmed is True` 才 execute——未确认只出预览不落库
  • 网关审批流：`/agent/approval/create` → `confirm`/`reject`，审批点集中在结论出口
  • 验证转人审：verify 不一致 → `needs_review` 标人工复核(不自动回滚)

权限分级驱动干预

  • 四级角色：不同 `minimum_role` 决定谁能发起(如故障转移/废弃需主任)
  • `need_approval` 标记高风险意图强制走审批
  • 误报由分级人审消化(资深/初审)，而非牺牲 recall
本质：把数据库事务的"提案→审批→提交→回读"思路搬到 Agent 写操作——人是最终门，模型只做提案。

⑦ 审计

audit_log 表 append-only，只在两处写：governance-blocked 和 verify(执行后)；execute 本身不写审计。

字段trace_id / intent / action / actor_role / status / success / need_approval / before_state_json / after_state_json / verify_checks_json / metadata_json
before/afterbefore = preview_result(改前预估)，after = tool_result(改后实况)——可比对"批准的 vs 执行的"
查询`/agent/audit/{trace_id}` 按链路查；`recent_audit_rows()` 供管理台读回
success 口径verify 全通过才 `success=true`；回读不一致降为 false + `status=needs_review`

⑧ 安全边界

流程层

  • 确定性 workflow 包住 LLM，LLM 只在 node 内
  • 写操作永不直接落库(preview→confirm→execute→verify)
  • 故障转移批量改带 `LIMIT 50` 防误伤

权限层

  • 四级角色层级 `user_level < required → blocked`
  • 高危缺实体兜底(机台故障缺 machine_id → block)
  • 未知意图 → block

数据层

  • 本地 Qwen，敏感数据不出厂(privacy-gateway)
  • 需外部复核才脱敏后发出

防幻觉层

  • `answer_grounded` + `evidence_source=sqlite`
  • `response_must_not_contain`(订单不存在禁编机台/日期)
  • `max_retrieval_steps` 防 agentic RAG 无限检索

⑨ 结果反馈

即时反馈verify 回读 DB 生成 `checks[]`(每项 name/passed/detail)；respond 把结构化结果转人话，带假设与影响面
可观测Langfuse/LangSmith trace 每节点；eval 指标 rule_pass_rate / p50 / p95 / judge score / escalation rate
数据飞轮线上 `audit_log` → `mine_eval_candidates` 挖候选 → 人审晋级 `online_hard_cases.json` → `run_scheduled_eval` 回归。评测集从真实失败长出来
防退化CI 三 job：audit(skill 健康 5检查) → rule-eval(无 LLM,每次) ∥ full-eval(含 judge,定时)；`rule_pass_rate≥1.0` 才 exit0
