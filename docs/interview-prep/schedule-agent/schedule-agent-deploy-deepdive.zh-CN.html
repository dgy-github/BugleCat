确定性 workflow 包住 LLM，写操作全过治理链，质量靠评测门禁 + 数据飞轮兜住。 这两块（写治理、评测）最容易被追问——本页按真实代码逐节点画流程，配「面试要点」和「易错点」。

🛡 四段治理链🧪 评测体系

🛡 流程图 A · 写操作四段治理链（governance → preview → execute → verify）

节点顺序 rewrite→route→…→governance→preview→execute→verify→respond。核心信条：确定性 workflow，只有 node 内需推理才让 LLM 决策；写操作永远不直接落库。

面试要点（四段各一句 + 信号字段）
  • ①治理 governance：角色层级 业务员0<工艺员1<主任2<厂长3（层级在代码 ROLE_HIERARCHY，per-intent 的 minimum_role/risk 在 intents.json）；blocked 三因：未知意图 / 权限不足(user_level<required) / 高危缺机台号。信号字段 governance_passed 布尔一票。
  • ②预览 preview：纯 dry-run 只读，产 preview_result{impact} 给人看；after_preview 用严格 confirmed is True 才放行——人在回路，未确认的写操作只出预览不落库。
  • ③执行 execute：真实 SQLite 落库；machine_failure 批量改带 LIMIT 50 防误伤；本节点不写审计。
  • ④验证 verify：按 intent 回读 DB 生成 checks[]；不一致不回滚，降级 needs_review 标人工复核 + 写审计（审计只在 governance-blocked 和 verify 两处写）。
  • 一句话：提案→预览→执行→回读四段闭环 + 角色权限 + 人在回路——把数据库事务的思路搬到 agent 写操作上。
易错点（面试官爱挖，别答错）
  • 角色层级不在 permissions.json（那只有 role_hierarchy），per-intent 权限在 intents.json；governance 读的是后者。
  • preview 节点不设 confirmed——由入口/人工注入；这是 human-in-the-loop 的落点。
  • verify 不一致不自动回滚，是标 needs_review 转人工——"宁可标复核不可静默生效"。
  • 写意图共 19 个（category=="write"）；破坏性操作(machine_failure/discard_order)要 主任(2)，无操作要求厂长(3)。

🧪 流程图 B · 评测体系（audit + golden + judge + 数据飞轮）

CI 三 job：audit 先跑（防退化）→ eval-rule（无 LLM，每次）∥ eval-full（含 judge，定时/手动）。门禁 rule_pass_rate ≥ 1.0 才 exit 0。

面试要点
  • 三层防护：audit(防 skill 退化，5 检查) → check_expected(~16 类确定性断言) → judge(LLM 补 3 维语义，可降级为规则)。
  • 门禁硬：rule_pass_rate ≥ 1.0 才 exit 0；CI 里 audit 先过才跑评测（needs: audit）。
  • 防幻觉断言：max_retrieval_steps(防 agentic RAG 无限检索)、response_must_not_contain(订单不存在时禁止编字段)、answer_grounded/evidence_source。
  • 数据飞轮：线上 audit_log → 挖候选 → 人工审 → 晋级 online_hard_cases.json → 定时回归——评测集从真实失败长出来，不是拍脑袋造的。
  • 一句话：有确定性判据就用确定性断言，judge 只留给语义维度且必须能降级——呼应"确定性优先于 LLM judge"。
易错点
  • 实际是 44 用例 / 11 类（README 表 + JSON 自述"5 路径×4 场景"），别说"8 类"。
  • audit 的 conflict 项是 warning 不阻断（passed 恒 True），只有 blocking 项计入门禁。
  • bench_chunking / lab_dpo_demo 是离线 lab，不进 CI 门禁；主线门禁是 eval.runner(golden+online) + eval.audit。
