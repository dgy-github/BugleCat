🧪 排产评测体系详解（复习版·重点在"为什么"）

闪卡只给点，这份把每个点讲透。全部锚 eval/ 真实代码（audit.py / judge.py / runner.py / README）。

先纠一个容易绕晕的：其实是"两套东西"，不是一个"三层"。
① audit.py = 独立的"skill 防腐烂体检"（不跑用例、不调 LLM，只查意图系统本身有没有烂）。
② eval runner = 跑 44 条 golden 用例的三层评测：L1 规则断言 → L2 LLM-judge → L3 Tracing。
你稿子里说的"三层防护 audit→check_expected→judge"是把 audit 也算成一道防线的讲法，没错；README 里的"三层"专指 eval 内部的 L1/L2/L3。两种讲法都对，别被面试官绕。
一句话理解：audit 保证"意图系统没烂"，eval 保证"跑起来结果对"；CI 里两个都过才放行。核心信条贯穿其中——能用确定性规则判的（L1/audit）就不用 LLM judge（L2）。

🩺 A. audit.py —— Skill 防腐烂体检（5 项）

为什么要它：意图系统会随业务演化而腐烂——你不断加新意图，老意图的触发词悄悄被抢、覆盖出现空洞、route.py 里堆下永不触发的死代码。腐烂是静默的，不体检没人发现。audit 就是上线前的"体检"，不跑用例、不调 LLM，纯查意图配置本身健康度。
blocking① dark_skills（死意图）
查：某意图的所有触发词都识别不到自己（永远触发不了）。机制：遍历该意图每条 trigger_phrases，拼成完整话跑 classify_intent，若命中的不是自己→这条 trigger 失效；全失效=dark skill。防：加新意图后老意图触发词被抢命中，老意图变死代码。
warning② trigger_conflicts（触发词冲突）
查：同一短语被多个意图共用（如"插单"既属 insert_order 又属 emergency）。这会让两个意图打分接近→路由不稳。只 warning 不阻断——重复允许存在，但要人知道这里有歧义风险。当前 4 个短语共用。
blocking③ self_recognition（自识别率）
查：每个意图的触发词命中自己的比例，<50% = 高风险 skill（说明触发词写得没区分度、容易被别人抢）。
blocking④ coverage（用例覆盖率）
查：golden cases 覆盖了多少意图。没被任何用例覆盖的意图=改了它没人会发现（回归测不到）。当前 23/23 = 100%。
blocking⑤ orphan_intents（孤儿意图）
查：route.py 里有 code == "xxx" 的加分逻辑，但 intents.json 里没定义这个意图→"幽灵代码"（这段加分永远不触发）。用正则扫 route.py 的引用 − intents.json 的定义。
面试金句：4 项 blocking（dark/self_recog/coverage/orphan）失败直接阻断 CI，1 项 warning（conflict）。"我给意图系统做了体检，防它随业务演化悄悄腐烂"——这是资深信号，大多数人只测功能、不测"配置系统本身有没有烂"。

📏 B. eval L1 —— 规则断言（~16 类，确定性、零成本）

为什么是第一层、还是硬门禁：这些判据都是确定性的（意图对不对、路径含不含 execute 是二值），能用规则判就绝不用 LLM judge（信条）。零成本、可复现、2 秒跑完 44 条。

每条 golden 用例声明一组 expected 字段，runner 比对实际 vs 期望。~16 类字段按管线分层：

层expected 字段断言什么
意图intent_code / confidence_min·max / entities / is_write / missing_entities选对意图、置信度区间、实体抽对、读写判对、该缺的实体缺了
治理governance_passed治理该过/该拦
路径path / path_must_contain / path_must_not_contain走对节点链（如只读 must_not_contain execute）
检索query_plan / tool_name / rag_retriever / max_retrieval_steps该不该检索、用对 SQL 工具、用对 retriever(hybrid/graph)、检索步数不超限
证据answer_grounded / evidence_source有据、来源是 sqlite
输出response_must_contain / response_must_not_contain输出层硬断言（订单不存在→禁含机台/日期，防编造）
关键理解：这不是"答了没"，是选对意图→走对路径→用对检索→有据→不编造整条链的确定性校验。所以"100% 规则通过"才有意义。

🚦 C. CI 门禁 —— rule_pass_rate ≥ 1.0

· 跑 44 条 golden 的 L1 规则检查，必须 44/44 = 100% 才 exit 0；低于阈值 exit 1，挡住合入/部署。
· 为什么是 1.0 不是 0.95：规则断言是确定性二值（意图对就是对），错一条=真回归，没有"差不多"。0.95 只允许本地临时排查用，CI/部署固定 1.0。
· 为什么快：L1 不调 LLM，纯管线逻辑，P50/P95 = 3ms/28ms，44 条 2.25s 跑完。
⚠️ 别把两个 P95 说混了！
这里的 28ms 是规则 eval 的延迟（不调 LLM，只跑路由/治理逻辑）。
之前说的 端到端 P95=4702ms 是 tracing 里含 LLM 调用的延迟（慢在 LLM 那 4588ms）。
被追问时说清："规则回归 2 秒跑完是因为不打模型；生产端到端慢是因为要等 LLM"——两个数字不冲突。

🤖 D. eval L2 —— LLM-as-judge（3 维 1-5，带降级）

为什么 judge 只当第二层、不当硬门禁：语义质量有主观性、成本高、还可能网关不可用。硬门禁交给 L1 确定性判据；judge 只做语义补充评估。
· 3 个评分维度（judge.py 的 prompt 写死）：相关性（是否针对问题）/ 准确性（事实对不对、关键信息有没有引具体数据）/ 完整性（是否覆盖 criteria 全部要求）。给 1-5 整数。
· 降级机制：网关挂了 _judge_with_llm 抛异常 → 自动降到 _judge_with_rules：从 criteria+state 提关键词，算命中率→分数（≥0.9→5 / ≥0.7→4 / ≥0.5→3 / ≥0.3→2 / else 1）；报告里 method 字段标 llm 还是 rule，可复现。
· 容错：三级 JSON 解析（直接 parse → 去 markdown 代码块 → 正则提第一个 {...}），score 钳到 1-5。
被追问"judge 打不准怎么办"：留人工校准子集验 judge-human 一致率，<0.9 先修 judge；能转成确定性断言的（L1）就不用 judge。这是"有确定性判据别用 LLM judge"信条的落地。

📡 E. L3 Tracing + 数据飞轮

· L3 = LangSmith Tracing：设 LANGSMITH_API_KEY 自动启用，每个 invoke 有完整 trace，看节点耗时/State 变化/失败链路；无 key 自动跳过不影响评测。
· 数据飞轮：线上 audit_log → mine_eval_candidates 挖候选 → 人审 → 晋级 online_hard_cases.json → run_scheduled_eval。评测集从真实失败里长出来（呼应你之前的 Bad-case 回流：响应异常自动修、业务理解异常才送人标）。
