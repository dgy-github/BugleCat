Q0 · 总纲（场景迁移）
题目：** 同一套 agent harness 换一个业务场景，哪些环不变、哪些环要重新「承重」？拿你的 coding agent 举例。

题目： 同一套 agent harness 换一个业务场景，哪些环不变、哪些环要重新「承重」？拿你的 coding agent 举例。

  • 考点： 驾驭工程的可迁移性 + 「场景决定承重」的判断力。
  • 答题骨架： 1. 不变的骨架：prompt 钉角色边界 / context 供可信数据 / 工具面收窄副作用 / ground-truth 校验 + 人审兜出口 / LLM 原始输出不直接落地。 2. 变的是承重：任务是 LLM-native（语义比对本身是主活）还是 LLM-as-interface（主活外包给确定性系统）？→ 决定 LLM 是主判断者还是翻译官。 3. 风险形态：最怕假阴性（合规漏判）还是假阳性（排产/编码幻觉方案）？→ 决定保守方向。 4. nanocodex 落点：编码 agent 副作用大（改文件/跑命令），所以权限环承重；若换成只读分析 agent，权限退居次要、检索/上下文环承重。
  • 一句话： 同一套方法论——合规长成 RAG+judge、排产长成 NL2建模+solver、编码长成「沙箱+审批+压缩+best-of-N」；骨架同，承重随业务。
Q1 · 权限 【必刷】
题目：** 你的 coding agent 怎么控制权限？为什么不能靠 prompt 写一句「不许删库」就完事？

题目： 你的 coding agent 怎么控制权限？为什么不能靠 prompt 写一句「不许删库」就完事？

  • 考点： Guardrails 环 · 安全建在代码不建在措辞。
  • 答题骨架： 1. 两道正交纯函数：SandboxPolicy 判「物理能不能写」（三档模式 + 词法路径包含）⊥ Approver::classify 判「越界了怎么办」（四档策略 → 三态 AutoApprove/Ask/AutoDeny）。 2. 三层解耦：policy（物理）/ approval（越界）/ prompt（人类提示，住 ncx-core 不在 sandbox crate，保持沙箱纯决策）。 3. 危险命令：untrusted 三重过滤，7 条危险正则先跑——rm -rf 即使被可信命令引导也当场拦。 4. 为什么不靠 prompt：prompt 是软约束，注入/抽风能绕；不可逆写操作物理隔离——release 类工具 agent 根本没有（能力剥夺，不是劝阻）。PolicyExecutor 只做容器（Job Object + 超时），决策到它之前已定死。
  • 一句话： 安全边界永远建在代码上，不建在措辞上；codex 给了词汇（3 沙箱/4 审批），我把它做成可单测、可回放的纯函数系统。
  • 换业务： 只读分析 → 权限退次要；金额/退款/下达类业务 → 补「提案权 / 下达权物理分离」（agent 只能 submit_for_approval，release 由审批系统触发）。
Q2 · 编排 / 多 agent 通讯 【必刷】
题目：** 你的父 agent 和子 agent 之间怎么通讯？有没有消息总线？

题目： 你的父 agent 和子 agent 之间怎么通讯？有没有消息总线？

  • 考点： Workflow 环（多节点）· 通讯设计的第一性。
  • 答题骨架： 1. 没有消息总线、没有 peer 对话。 三条真实通道：① prompt 下发（状态按值序列化进每个全新无状态子会话）；② 文件系统隔离-提升（代码改动的真 IPC：每个 worker 改私有拷贝，verifier 选 winner 后 promote 回真 workspace）；③ PASS/FAIL/BEST 裁决文本回灌闭环。 2. 能力剥夺：reason() 节点（classify/plan/verify）走空 registry，代码级物理拿不到工具。 3. 为什么这样：无状态子会话可并行、可重跑；「隔离-然后-提升」恰好解决并行 apply_patch 撞同一文件的真实 bug。
  • 一句话： 子 agent 不「对话」——文本是下行通道，磁盘才是代码的真 IPC，裁决文本是回路。
  • 换业务： 需要 peer 协商的业务（售后：决策↔供应链↔风控）→ 补 A2A 的 query 消息类型，但保留「父节点唯一中枢」防协商环路/死锁。
Q3 · 离线演化 / 安全边界 【必刷】
题目：** 你让 agent 离线自动优化自己，怎么保证这个过程不会引入安全风险？

题目： 你让 agent 离线自动优化自己，怎么保证这个过程不会引入安全风险？

  • 考点： Feedback 环 + 训练接缝即安全边界。
  • 答题骨架： 1. 离线只演化 genome = system prompt + 工具描述（纯文本），绝不动行为/权限。 2. NCX_GENOME 是训练与运行唯一接缝；可证明 no-op（空/格式错 → 字节级回退默认脚手架）。 3. 执行始终过沙箱 → 一个被不可信失败轨迹喂养的 teacher 也无法注入新能力：训练接缝与安全边界是同一条线。 4. sentinel 暗号门：无法证明注入确实生效前拒绝训练——防「离线全绿是假象」。
  • 一句话： 能演化的只有文字，执行永远过沙箱——离线训练改不动安全边界。
Q4 · 上下文压缩 【补充】
题目：** 长任务把上下文撑爆了怎么办？为什么你的压缩是「非破坏性发送时视图」？

题目： 长任务把上下文撑爆了怎么办？为什么你的压缩是「非破坏性发送时视图」？

  • 考点： Context 环。
  • 答题骨架： 1. for_model_edited 构建发送时视图，self.messages 原始历史不动（非破坏）。 2. 两趟：先把旧 tool 结果压到上限 → 仍超限则在 user 边界丢最旧前缀。 3. 硬规则：切点绝不落在 tool_result——否则历史以孤立 tool 消息开头，下一次请求 400。 4. 为什么非破坏：压缩是有损猜测，保留原始才敢激进压——resume / 回放 / 换模型重算都要原始。
  • 一句话： 压缩是「发送时的一次性视图」，不是把历史真删了——原始不可变，才敢激进压。
  • 换业务： 编码 → keep 最近代码 diff；客服/售后 → keep 用户原始诉求 + 订单号（不同的「保留优先级」）。
Q5 · 确定性校验 vs LLM judge 【补充 · 跨场景元原则】
题目：** critic / 校验这一环，什么时候用确定性校验、什么时候才上 LLM judge？

题目： critic / 校验这一环，什么时候用确定性校验、什么时候才上 LLM judge？

  • 考点： Guardrails/Evals 的通用判据（面试高频，能体现判断力）。
  • 答题骨架： 1. 有数学/可程序化判据 → 永远优先确定性：排产的 validate_schedule、权限的 can_write、编码的 verify PASS/FAIL。 2. 只有语义判据 → 才上 LLM judge：如合规「该条款是否支持该结论」，且 judge 必须用人工校准集对齐（agreement ≥ 0.9 才可信）。 3. nanocodex 的 verify 是确定性裁决文本（PASS/FAIL/BEST），不再挂一个大模型评审。
  • 一句话： 有确定性判据就别用 LLM judge；judge 只留给纯语义场景，且必须校准。
Q6 · 记忆 【选刷】
题目：** agent 的记忆怎么设计，才不会用过期经验污染当前判断？

题目： agent 的记忆怎么设计，才不会用过期经验污染当前判断？

  • 考点： Memory 环。
  • 答题骨架： 1. recall 注入时标为「线索而非事实」（RECALL_HEADER），不当 ground truth 用。 2. 写入只收 CONFIRMED + 精确去重 + 上限；consolidate(0.85) 启动即幂等去重防近重复堆积。 3. 为什么：记忆是弱信号，当事实用会把过期经验变成「幽灵约束」。
  • 一句话： 记忆进上下文是「线索」不是「事实」，写入只收确认过的——防幽灵约束。
  • 换业务： 编码 → 项目事实/习惯；客服 → 用户偏好 + 租户隔离（A 的记忆不能泄漏进 B）。

  • Q0 做开场框架，任何 agent 系统设计题都能用它起手。
