🔑 ① 承重点：没人在场时 Ask 怎么办
fail-closed → Deny，复用双层门不造新权限

问题approval.rs 注释明写：Decision::Ask 的真正弹窗"是上层 CLI/GUI 的事"。交互模式下人来点 yes/no；定时器无人值守，没人回答。这是任何"自主/后台 agent"的真正命门，不是计时。

答案调度器是一个新的"上层"，它给出的 Ask 解析器是纯粹的 fail-closed：Ask → Deny；AutoDeny 绝不软化；只有 AutoApprove 放行。即定时任务天然只能做"能自动批"的活（untrusted 下的只读白名单 / on-request 下的非越界操作）。

为什么优雅不发明任何新权限——classify() 一行不改，双层门（can_write ⊥ classify）原样复用。这正是 nanocodex 既有的"能力剥夺"范式：read-only 让 can_write 恒 false；unattended 让 Ask 恒 Deny。安全建在代码不建在措辞。

诚实边界代价=定时任务能力受限（默认干不了需要人批的写）。想让它跑写操作，必须在 schedules.toml 里显式预授权一个不会产生 Ask 的组合（如 approval=never + sandbox=workspace-write：越界 auto-deny、界内自动跑），把授权决定前移到人写配置那一刻，而不是运行时。

⚙️ ② 触发机制三选一
推荐委托 OS 调度器（回扣 5.5ms 冷启动）

A. 委托 OS 调度器（推荐）把 ncx -w … "prompt" 注册进 Win Task Scheduler / cron / launchd。零 daemon、随开机存活、错过的触发 OS 能补跑。关键理由：agent ~5.5ms 冷启动让"每次触发新起一个进程"几乎免费——单发 CLI 的快启动本就是让 per-fire spawn 成立的前提，单文件仍是单文件。代价=要写一层跨平台注册抽象（三个后端）。

B. 自带常驻 daemonncx schedule daemon 里跑 tokio 定时轮。跨平台统一，但违背"单发快启动"气质、进程得一直活着（谁拉起/重启？）、等于重造 cron。不推荐作默认。

C. 复用 Temporal Schedules视频子 crate 已依赖 Temporal，它自带 durable、崩溃恢复、exactly-once 的 Schedules。只在视频那种长时/贵/须恢复的作业上用；给"每晚跑一次测试"这种轻任务上 Temporal 是杀鸡用牛刀（要跑 Temporal server）。

结论核心 CLI 走 A；视频/长作业走 C；B 明确不做。

🏃 ③ 无头执行：复用既有单发路径
不造新执行入口

现成ncx [OPTIONS] [PROMPT] 已是"跑一轮→打印→退出"。定时任务触发时就是拼一条这样的命令，可带 -r(接续会话) 或 -o(走编排)。执行路径、上下文压缩、双预算(--max-iterations/--max-tool-calls)全部复用。

输出去向无人看 stdout → 结果落既有 session log + 一份 run-history（记 exit code / 末条回复 / 触发时间）。这份 run-history 就是排产 audit_log 的同构物——留痕可回溯。

🗂 ④ 数据模型：schedules.toml
跟 config.toml/mcp.toml 一个规矩

位置~/.nanocodex/schedules.toml（沿用既有 config.toml/mcp.toml 约定，不新造目录）。

字段（每条一个 [[schedule]]）id(稳定键，OS 任务名/锁名) · cron(表达式) 或 at(一次性) · tz(时区，别踩 UTC/本地混用) · workspace · prompt(或 resume=true/orchestrate=true) · model/profile · sandbox/approval(默认 read-only + on-request，最保守) · max_iterations/max_tool_calls · on_missed(skip|run-once) · overlap(skip|queue，默认 skip)。

解析沿用 config 层的 toml 加载；纯数据、零 I/O 校验（cron 表达式合法性、policy 合法性在 sync 时一次性查，坏配置早失败）。

⌨️ ⑤ CLI 形态：管理 flag（不引 clap）
照 --history/--memory-merge 范式

手写 parser 已有一批"做一件事即退出"的 flag。定时器加同款、不引 clap（守住启动快/二进制小）：

新增 flag--schedule-sync(读 toml → 注册/更新 OS 任务，然后退出) · --schedule-list(列已注册) · --schedule-run <id>(手动触发一次，测试用) · --schedule-remove <id>。触发时 OS 实际调用的仍是普通 ncx -w … "prompt"，无需新执行子命令。

取舍不做交互式 schedule 子命令树（那会把手写 parser 推向 clap）；声明式 toml + 少量管理 flag 更贴 nanocodex 气质。

🔒 ⑥ 重叠触发 / 幂等（回扣排产并发）
per-id 锁跳过 —— 同一把锁的思路

问题上一次还没跑完，下一次触发到了（长任务）。

做法每个 id 一把轻量锁文件（~/.nanocodex/locks/<id>.lock，含 pid+起始时间）：拿不到锁 → overlap=skip 直接跳过并记一条 "skipped: still running"。这正是排产订单级写锁的同构——"有在跑就别重入"。锁要带 TTL/陈旧 pid 检测（进程崩了不能永久锁死），和排产那个坑一模一样。

🚧 ⑦ 分阶段实现计划
MVP 一周内 → 再加固

MVP①新 crate ncx-schedule（或 ncx-cli 下一个模块）：toml 模型 + 无人值守解析器(Ask→Deny) + 锁。②只做一个后端（先 Windows Task Scheduler，因你在 win）。③管理 flag --schedule-sync/list/run。④触发命令 = 现成单发。⑤run-history 落盘。

加固cron/launchd 后端 + on_missed 补跑 + 结果通知（写文件/webhook）+ 预授权写任务的显式校验 + 单测（解析器 Ask→Deny 的属性测试是重点）。

🧭 ⑧ 不做的边界（诚实）
明确划掉的范围

· 不做自带调度守护进程（重造 cron，违背单发气质）。

· 不做运行时人审兜底（无人值守本就没人审；要写操作就配置期预授权，别指望运行时）。

· 不把定时器塞进沙箱 crate（它是"上层"，approval.rs 的分层边界要守住）。

· 轻任务不用 Temporal（依赖太重）；重/长/须恢复作业才上 Temporal。

· MVP 不做分布式/多机（单机 OS 调度足够；多机再谈共享锁）。

🎤 ⑨ 面试话术
30 秒总纲 + 被追问

30 秒"给 agent 加定时器，我不会去写一个调度守护进程——我的 agent 冷启动 ~5.5ms，直接把无头单发命令委托给 OS 调度器，每次触发新起一个进程就行，单文件还是单文件。真正的难点不是计时，是'没人在场时 approval 的 Ask 怎么办'：我让调度器这个上层给出一个 fail-closed 的解析器——Ask 一律 Deny、AutoDeny 不软化、只有 AutoApprove 放行，classify() 一行不改。定时任务因此天然只能干能自动批的活；要跑写操作，必须在配置里显式预授权一个不产生 Ask 的策略组合，把授权决定前移到写配置那一刻。"

被追问"为什么不自带 daemon"daemon 得一直活着、谁拉起谁重启、等于重造 cron，还违背单发快启动的气质；OS 调度器还免费给我"错过补跑"和"开机存活"。

被追问"重叠触发/机器关机"per-id 锁文件跳过重入（跟我排产订单锁同构，锁要带 TTL 防崩溃锁死）；关机错过的触发靠 OS 的 run-once-after-missed。

被追问"这算不算引入新攻击面"没有新权限逻辑——双层门原样复用，新增的唯一决策是"无人时 Ask→Deny"，是收紧不是放宽；能演化/被配置的最多是"跑哪条 prompt"，执行始终过沙箱。呼应 ncx-forge"训练接缝即安全边界"的同一信条。

🧾 一句话总纲

nanocodex 加定时器 = 委托 OS 调度器 spawn 无头单发（5.5ms 冷启动让 per-fire 进程免费）+ 声明式 schedules.toml（沿用既有约定）+ 无人值守解析器 Ask→Deny 的 fail-closed（复用双层门、零新权限、把授权前移到配置期）+ per-id 锁（同排产并发思路）。难点从来不是计时，是"没人在场时的审批语义"。
