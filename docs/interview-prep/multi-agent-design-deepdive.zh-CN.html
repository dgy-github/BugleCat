① 多 Agent 交互设计

🕸 DAG 编排，不是链式对话
depends_on + 拓扑分层 + 成环即报错

现状（真代码）Coordinator 把 ExecutionOrder decompose 成带 depends_on 的 Task；_topological_layers 按依赖分层，层内 asyncio.gather 并行、层间串行；循环依赖直接 raise ValueError("cyclic task dependency")——交互拓扑在装配期就是合法 DAG，不靠运行时对话涌现。

为什么这样多 Agent 最怕"你问我我问你"的死循环和无界对话。用 DAG 把协作变成可静态校验的依赖图，依赖没就绪的任务记 task.skipped 而不是硬等。

✉️ 类型化 A2A 信封（trusted/untrusted 分部）
消息带来源标记，不是裸字符串

现状所有 agent 走统一 Message.request(from_agent,to_agent,task,run_id)，body 是 Part(kind,data,untrusted) 列表：session 上下文=可信内部部（untrusted=False）、knowledge/RAG 命中=不可信外部部（untrusted=True）。传输层可换：InProcess / HTTP JSON-RPC / SSE / RemoteAgentProxy + capability discovery。

交互的关键信封自带来源可信度——下游 agent 知道哪部分是"我方内部状态"、哪部分是"外部可能被投毒的内容"，这是防 prompt injection 的信息基座（呼应网关的 SECRET/PII 分级、nanocodex 的记忆"线索非事实"）。

🔍 检查交互：执行者 ≠ 复核者
独立复核·不降级·fail-closed（你问的"检查"）

现状（真代码）_review 单独找 Reviewer agent 对 Executor 的 artifact 按 task.acceptance 打分裁决，返回 {passed,score,reasons}。三条硬设计：

· 执行者产出、复核者独立判——防"执行者自证正确"（模型给自己打高分）。
· 红线：验收门禁绝不降级给小模型（Reviewer 恒 flagship tier）；系统减员（attrition）时 Reviewer strictness 反而调高到 ≥0.7——越缺人越严把关。
· fail-closed：Reviewer 报错记为未通过不崩整个 run；require_reviewer=True 时无 Reviewer 直接判不通过（不静默放行）。

交互形态Executor→（EventLog）→Reviewer 单向复核，不是 executor 和 reviewer 对话辩论；裁决 review.done 事件回流 Coordinator 决定 done/failed。

诚实边界无 LLM 时 _rule_verdict 是占位 stub（默认给 0.75 通过）——真规则/真 LLM 裁决要补；这是"参考实现"的诚实缺口。

⚙️ 并发 + 共享状态锁 + HITL 断点续
Semaphore 默认 1·PolicyGate 锁·durable resume

现状并发 asyncio.Semaphore(concurrency) 默认 1（串行、行为保守），层内可并行；预算/账本等共享状态统一过 PolicyGate 的锁（并发安全）。HITL：task.needs_approval→发 task.input_required 事件挂起→resume(run_id,task_id,human_input) 从 EventLog replay 断点续跑（durable）。单任务 task_timeout 兜底，挂死的 agent 不拖垮整个 run。

回扣"同订单写锁"的多 Agent 版——共享状态的并发一律走一把闸，和排产订单锁、定时器 per-id 锁同一思路。

② 架构 · 观测 · 评估

🏗 分层装配（Milestone 增量长大）
最小闭环 → 逐层接治理/韧性/观测/门禁

现状Runtime 把组件装配成系统，按 Milestone 增量：M2 最小闭环(Coordinator→Router→Executor→Reviewer) → M4 Breaker/Checkpoint → M5 Mobilization/Reserve → M6 Governor → M7 Tracer → M8 Eval gate。每个能力 opt-in、默认 OFF、不调用则行为不变（memory/knowledge 注入都是这规矩）。

架构取向组件都靠 set_xxx 注入、面向接口（Transport/Tracer/Governor 都是可换实现）——可测试、可逐步生产化，而不是一个大 God-Runtime。

🔭 观测"进控制环"，不是仪表盘
span/meter/score → health → 减员/熔断

现状（真代码）Tracer 三能力：span(name,actor)（包一次 agent 调用，记 status ok/error + duration）、meter(actor,tokens,cost,latency)（成本计量）、score(task_id,score)（在线质量打分）。recent_latency/recent_cost(actor,window=10) 给每个 actor 的滑动窗口。

承重洞察观测数据回喂控制环：meter→CapacityLedger.health→Mobilizer 减员/动员；score 过低→Breaker 熔断。所以观测不是"事后看的大屏"，是实时驱动降级与接管的信号源（源码注释原话："实时态势屏 + 黑匣子，看真实而非阅兵"）。留了 OpenTelemetry / Langfuse adapter 接缝。

诚实边界真实实现目前是 InMemoryTracer（测试/开发用），OTel/Langfuse 是接缝未接线；生产化要接真实后端 + 滑动基线排除异常样本（呼应排产可观测优化）。

🎯 评估：硬门禁 + 数据飞轮
≥0.8 才上线·EventLog→蒸馏训练集

现状（真代码）EvalHarness(threshold=0.8)：跑 EvalCase（order+expected+weight）→ 加权均分 → gate() ≥0.8 才允许"上线"（硬门禁）。评分 completion*0.5 + avg_review*0.5，任一用例 review 未过=0 分（一票否决）。ChaosDrill 主动演练失败：工具失败/超预算/远程 agent 不可用/review 拒绝/权限违规。

飞轮export_trainset_async：EventLog replay → 按 task_id 分组 → 标 success/failure → 导 jsonl 训练集（蒸馏小模型 / badcase 回流）。这和排产的 mine_eval_candidates→online_hard_cases、你上一轮的 Bad-case 回流飞轮是同一台飞轮。

③ 业务设计闭环：有没有类似架构方案？——有，同一副骨架

🧭 一副骨架，单/多 Agent 通吃
command→govern→execute→review→log→observe→eval→飞轮

你问"业务设计整个闭环是否有类似架构设计方案"——有，而且就是你已经在两个项目里跑通的那一副：

命令(Order/意图) → 治理(先治理再执行) → 执行 → 独立复核 → 事件留痕 → 观测进控制 → 评估硬门禁 → badcase 飞轮

多 Agent 版相对单 Agent 版只在"执行"这一环从单点变成编队（DAG+能力路由+角色分离+韧性），骨架、治理位置、复核位置、飞轮位置完全一致。所以它不是新范式，是同一套驾驭工程换了承重。

🌉 桥：nanocodex best-of-N → campaign
受限编排 → 可治理可观测的多 Agent runtime

演进叙事nanocodex 的 best-of-N 已是受限多 Agent：进程内、无消息总线、文件隔离做 IPC、一个 verify 选 winner。campaign 是完整多 Agent：跨进程类型化 A2A 消息、EventLog 事件溯源、独立 Reviewer、DAG 编排、韧性（Breaker/Mobilizer）、HITL durable resume、观测进控制环。

面试用"我先在 nanocodex 用最省的结构（文件 IPC + 单 verify）验证了'编排靠结构不靠更聪明的模型'；当协作要跨进程、要审计、要治理、要演练时，就长成 campaign 这套可指挥·可观测·可演练的 runtime——同一套驾驭工程，承重从'单机编排'升到'分布式治理'。"

🎤 面试话术（三点各一句）

① 交互："多 Agent 交互我不做自由对话——用 DAG + 类型化 A2A 信封：任务带依赖、拓扑分层、成环直接报错；消息按 trusted/untrusted 分部标来源。检查交互是执行者≠复核者的独立复核，验收绝不降级给小模型、无复核者 fail-closed。"

② 观测评估："观测我做成进控制环不是仪表盘——span/meter/score 回喂 health，驱动减员和熔断，看真实而非阅兵；OTel/Langfuse 留了接缝。评估是硬门禁 + 飞轮：加权≥0.8 才上线、任一复核不过一票否决，EventLog replay 导训练集回流蒸馏。"

③ 业务闭环："业务闭环有现成骨架：命令→治理→执行→独立复核→留痕→观测→评估门禁→飞轮。单 Agent（排产）和多 Agent（campaign）同一副骨架，只是执行那一环从单点变编队。所以不是每个项目重新发明架构，是同一套驾驭工程换承重。"

🧾 一句话总纲

多 Agent 设计的三个深化：交互=DAG+类型化 A2A 信封+执行者≠复核者（不是对话）；观测=span/meter/score 进控制环驱动减员熔断（不是仪表盘）；业务闭环=命令→治理→执行→复核→留痕→观测→评估门禁→飞轮的同一副骨架，单/多 Agent 只差"执行"是单点还是编队。配套完整框架见 campaign-multi-agent-design-brief（Command/Formation/A2A/Governance/Rehearsal）。
