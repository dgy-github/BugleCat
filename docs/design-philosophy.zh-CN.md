# nanocodex 设计哲学（中文 · 深度版）

> 这份文档不罗列功能。它做四件事：从**硬约束**推导每个设计；用**经济学**
> 证明这些设计为什么划算（以及何时不划算）；列出每个决策的**被否决替代方案
> 与代价**；给出每个机制的**失效模式与支撑它的不变量**。最后诚实地划出
> 这套设计**不解决**什么。
>
> 用法见 [README](../README.md) / [README.zh-CN](../README.zh-CN.md)。
> 代码在 `rust/`（当前发布线）。

---

## 序：方法论

设计一个 agent 框架时，最容易犯的错是“功能驱动”——看到别人有 plan、有
multi-agent、有 memory，就都加上。nanocodex 反过来：**先承认约束，再让每个
机制从约束里被逼出来**。如果一个机制不能追溯到某条约束，它就是装饰，应该删掉。

所以本文的主线是一条推导链：

```
约束（不可改变的事实） → 推论（必然的设计方向） → 机制（具体落点） → 代价 + 失效模式
```

## 第一部分：五条约束，与它们逼出的设计

### 约束 1 —— 模型是瓶颈，框架不是

agent 的工作是 I/O 密集（等模型、等工具），不是 CPU 密集。**最大的不可改变量
是主模型的推理上限**：plan 和 verify 都跑在主模型上，所以任何编排的产物质量
都有一个硬天花板 = 主模型能判断对的范围。

- **推论**：不要试图“用框架变聪明”。框架能做的只有**抬下限**（把模型偶尔能做
  对的事，变成稳定做对），不能**抬上限**。
- **落点**：分层编排、best-of-N、verify、递归分解——全是“多花算力换稳定”，
  没有一个声称能让模型推理超出自身。
- **真正的上限杠杆**：换更强的主模型。`DeepSeekProvider` 是 OpenAI 兼容的，
  改 `base_url`/`api_key`/`model` 零代码即可换。**这条约束决定了所有结构性投入
  都是“边际改良”，把它写进文档是为了防止过度投资框架。**

### 约束 2 —— 模型调用是非确定性的

同一个 prompt 两次调用结果不同。**单次成功不能证明能力，单次失败不能证明无能。**

- **推论 A**：度量必须用**重复 + 通过率**，不能用单跑。
- **推论 B**：既然单个尝试不可靠，就让**多个独立尝试并行**，再选最好的
  （best-of-N）。
- **推论 C**：模型自己说“做完了”不可信，需要一个**独立的 verify 步**，且
  verify 默认应**怀疑**（见不变量“fail-loud”）。
- **落点**：bench 的 `--repeats`（默认 3）出 k/N；编排器的 best-of-N + verifier
  + 闭环重试。

### 约束 3 —— 上下文窗口稀缺且按 token 计费

把“可能用到的一切”塞进 prompt，既贵又稀释注意力，还撞窗口上限。

- **推论**：默认应该是**少给**，把“按需取回”做成一等机制；只有**索引**常驻，
  **正文**按需加载。
- **落点（三处同构）**：
  - Skills：系统提示只挂 `name + description`，`skill` 工具按需取正文；
  - tool_search：大注册表只挂核心工具 + 一个搜索入口；
  - 上下文编辑：本地历史完整，但**发送时**压缩旧工具结果、丢更老前缀；
  - 记忆：检索式注入（混合词法+语义排序），而非把整个记忆库塞进去。

### 约束 4 —— 强模型会“越权勤奋”

一个工具训练充分的强模型，只要手里有工具，就倾向于**直接动手**，哪怕你只让它
做判断。这是本项目实测踩到的坑（见第三部分机制 4）。

- **推论**：节点要**按职责限权**。让“判断/规划”节点**拿不到工具**，它就只能
  判断；让“执行”节点拿到工具。权限即角色。
- **落点**：`reason()`（无工具 AgentLoop）跑 classify/plan/decompose/verify；
  `run`/`run_worker`（带工具）跑实际执行。

### 约束 5 —— 一切外部内容都不可信

文件内容、命令输出、web/MCP 返回——都可能含注入指令。

- **推论**：**数据与指令必须分层**。外部内容永远当数据，不当指令；危险动作要有
  独立于模型的物理门控。
- **落点**：沙箱模式（能做什么）× 审批策略（越界怎么办）两条正交轴；所有动作
  过同一个 `ToolContext`/`ToolRegistry` 边界；hooks 可在工具前后做确定性拦截。

## 第二部分：经济学 —— “把省下的钱花在结构上”到底成不成立

第 0 条口号听起来漂亮，但它**只在特定条件下为真**。这一节把它做成可证伪的数学。

### 2.1 成本模型

设一次 worker 调用在便宜模型上成本为 `c_f`，在主模型上为 `c_m`，通常
`c_m / c_f` 是数倍到一个数量级。再加一个事实（本仓库 README 自述）：
**cache 命中的输入 token 比未命中便宜约 120×**——所以重复跑相似 prompt 时，
后续调用因 prompt 前缀缓存而进一步变便宜。这两点合起来，是“结构性多跑”能便宜
的物质基础：**flash 单价低 + 重复 prompt 命中缓存**。

> 这里不写死具体单价（会过时且因供应商而异）。结论用比值表达，对任何
> OpenAI 兼容后端都成立。

### 2.2 best-of-N 的期望通过率

设单个 worker 独立成功概率为 `p`，verifier **完美**时：

```
P(至少一个对，且被选中) = 1 − (1 − p)^N
```

- `p=0.6, N=1 → 0.6`；`N=2 → 0.84`；`N=3 → 0.936`。**边际收益递减**：从 1→2
  涨 0.24，从 2→3 只涨 0.10。这就是为什么 `workers` 默认 2、`high_workers` 默认
  3——再加 worker 不值那份 token。
- 但 verifier **不完美**：设它能在“有对的候选时正确选中”的概率为 `q`，则实际
  `P ≈ q · (1 − (1−p)^N)`。**`q` 是天花板**——verify 比 worker 弱时，加再多
  worker 也被 `q` 封顶。
- **由此得设计规则**：① verify 应跑在**不弱于 worker 的 tier**（所以 High 在
  main 上 verify）；② N 取个位数即可；③ verify 默认 fail（宁可重试，不可
  假阳性放行）。

### 2.3 闭环重试的期望

每轮整体通过概率约 `P`（含 verify），重试上限 `R`，则总通过
`1 − (1 − P)^(R+1)`，成本是轮数的线性叠加。`max_verify_retries` 默认 1：把
`P=0.85` 抬到 `0.978`，只多花一轮。**再多重试同样边际递减**，且每轮全价，
所以不默认开大。

### 2.4 递归的成本爆炸 —— 为什么必须设上限

递归分解看着优雅，但成本是**乘性**的。设一次分解出 `S` 个子任务，每个子任务是
一条 pipeline（≈ `1` plan + `N` worker + `1` verify = `N+2` 次调用），递归深度
`d`，则调用数量级是 `(S·(N+2))^d` 级别。

**实测的教训**：一次 High 任务，模型把它分解成 **13 个子任务**。即使只在深度 1，
`13 × (3 worker + plan + verify) ≈ 65` 次调用；而当时没配 `fast_model`，**全部
跑在昂贵主模型上**，于是 10 分钟窗口都跑不完。

- **由此得三个旋钮**（都在 `OrchestratorConfig`）：
  - `max_depth`（默认 1）：限指数的指数；0 = 完全关闭分解。
  - `max_subtasks`（默认 6）：限分支因子 `S`；超额**截断并 trace 明示丢了多少**。
  - `high_workers`：限每层的 `N`。
- **不静默截断**：截断会打 trace 行，因为“静默砍掉一半工作”读起来像“全做了”，
  是最危险的假象。

### 2.5 结论：ROI 的符号取决于两个条件

> 结构性投入（多跑/分治/复核）的净收益 **> 0 当且仅当**：
> **(a) 便宜 tier 真的便宜**（`c_f ≪ c_m`，且有缓存命中）；
> **(b) verify 真的能筛**（`q` 高，即 verify ≥ worker tier）。
>
> 当 `fast_model` 缺省（flash=pro，全程主模型）**或** verify 偏弱时，
> 这些结构是**纯成本、负 ROI**。这不是 bug，是经济学边界——文档把它写明，
> 是为了让使用者**先配 `fast_model`、再开 `-o`**。

## 第三部分：核心机制的取舍（候选 → 选择 → 代价 → 失效 → 不变量）

每个机制都给出：被否决的替代方案、为什么选当前方案、付出的代价、残余失效模式。

### 机制 1 —— 编排拓扑：分类驱动的分层图

| 候选 | 问题 |
|---|---|
| 单 agent ReAct 循环 | 简单，但所有任务一个待遇，难任务没有额外保障 |
| 静态 plan→execute | 总是 plan，简单任务被 plan 拖慢、被过度结构化 |
| **分类驱动分层图（选中）** | 先用一次便宜 classify 决定投入：simple 直跑 / medium 加 plan+verify / high 再加分解 |

- **代价**：多一次 classify 调用；分类错了会投入错配。
- **失效模式**：分类器保守，小任务普遍判 Medium（实测）。
- **支撑不变量**：分类错也不致命——Medium 仍有 plan+verify 兜底，是“安全的中间挡”。

### 机制 2 —— 并行策略：best-of-N vs 分工，及其张力的调和

这是整个编排器最微妙的设计张力：

- **best-of-N**：N 个 worker 做**同一件事**，彼此独立 → 并行安全，选一个 promote。
- **分工（divide work）**：N 个 worker 做**不同部分** → 但它们要写同一个工作区，
  并行会冲突，且无法“只采纳一个”，得合并。

**两者直接并存会冲突**。nanocodex 的调和方式：**用递归把“分工”转成“顺序的
best-of-N”**——

- 同一层内永远是 best-of-N（独立、并行安全）；
- “分工”发生在**递归的不同子任务之间**，而子任务是**顺序**执行的，每个子任务
  自己做完一轮 best-of-N 并 promote 后，下一个才开始。

于是分工不再需要并发写同一目录，张力消解。**这是“隔离-提升”不变量（见第四部分）
让递归得以成立的关键。**

- **代价**：子任务顺序执行，没有跨子任务并行，wall-clock 更长。
- **失效模式**：子任务之间若有循环依赖，顺序分解无法表达（需要人把任务拆对）。

### 机制 3 —— 隔离-提升 vs 共享工作区 vs 事务

| 候选 | 问题 |
|---|---|
| 所有 worker 直接写真实工作区 | 并行互相覆盖，best-of-N 根本无法实现 |
| 文件锁 / 事务 | 复杂，且模型发的是任意 shell/patch，锁粒度无法可靠界定 |
| **每 worker 一份工作区副本，胜者 promote（选中）** | `copy_tree` 到 scratch，verifier 选 BEST 后同步回真实工作区，其余清理 |

- **代价**：拷贝整个工作区（大仓库很贵——所以基准用小工作区，也提示生产中
  `-o` 的工作区不宜过大）。
- **失效模式**：拷贝失败时回退到真实工作区（无隔离）——降级而非崩溃。
- **支撑不变量**：隔离-提升 + 顺序，使递归子任务能看到彼此“已落地”的成果。

### 机制 4 —— 推理节点的工具策略（本项目踩坑得来的设计）

| 候选 | 结果 |
|---|---|
| 所有节点全工具 | **实测崩**：强模型在 classify 回合直接 `apply_patch` 把任务做了，分类永不快速返回，High 路径失控 |
| 只读工具（read_file/grep） | 能防执行，但需跨 crate 暴露工具子集，且模型仍可能读个没完 |
| **无工具 + 提示词声明（选中）** | `reason()` 用空 `ToolRegistry`；模型没有工具 schema，只能直接给判断/计划 |

- **代价/残余失效**：被剥夺工具后，工具训练过的模型有时会在 plan/decompose 里
  **幻觉出 `<tool_call>` 文本**而非产出内容。
- **缓解（两道）**：① 提示词明确“你没有工具、不要尝试读文件”；② `parse_subtasks`
  容错——`SUBTASK:` 缺失时回退解析编号/项目符号列表（实测模型常不守格式）。
- **教训**：**权限就是角色**。给判断节点工具，它就不再是判断节点。

### 机制 5 —— 渐进披露 vs 全量注入 vs 纯 RAG

- 全量注入：贵、稀释、撞窗口。
- 纯 RAG（外部向量库）：引入基础设施依赖与检索质量风险。
- **渐进披露（选中）**：始终可见的小目录 + 模型**自己决定**何时取正文。
- **代价**：多一次往返（模型得先调 `skill`/`tool_search`）；模型可能**不去取**
  本该取的正文（披露依赖模型判断）。
- **不变量**：索引-按需-取正文，是一个可复用形状，不只用于 skills。

### 机制 6 —— 视觉：单模型多模态 vs 双后端路由

- 强行让文本主模型吃图：很多便宜文本模型根本不支持。
- **双后端路由（选中）**：`has_image_block` 检测到图就切 `vision_provider`
  （`vl_*` 配置，缺省回退主端点）。
- **代价**：多一套配置；provider 请求层须对多模态 `content` 原样透传（已满足）。
- **失效模式**：未配 `vl_model` 时不路由，图 turn 落到主模型——降级而非报错。

### 机制 7 —— 记忆整理：每次 LLM 合并 vs 从不整理 vs 便宜常态+昂贵按需

- 每次启动都 LLM 合并：把昂贵操作压在热路径，启动变慢、烧钱。
- 从不整理：记忆越积越脏，检索质量下降。
- **便宜常态 + 昂贵按需（选中）**：每次启动跑**幂等的启发式去重**；LLM 合并只在
  显式 `ncx --memory-merge` 时跑。
- **不变量**：幂等——常态操作多跑几次不改变结果，所以可以放心每次启动都做。

### 机制 8 —— 上下文压缩：截断 vs 摘要 vs 确定性 digest

- 纯截断：丢信息且可能切断 tool_call/result 对，破坏消息合法性。
- 纯模型摘要：每次压缩都花 token。
- **双策略共一接口（选中）**：默认**确定性 digest**（零 API 成本、规则化）；
  可选**模型摘要**（花 token 换可读性）。tail 永远从 `user` 消息开始，不切断
  工具对。
- **不变量**：本地历史完整保留，只编辑**发送时视图**——可审计、可回溯。

## 第四部分：贯穿性不变量（机制背后的可复用原理）

把分散的机制抽象成几条**不变量**。它们才是这套设计真正的“理念”，机制只是其投影。

1. **隔离-然后-提升**：任何“可能搞砸”的并行/试探，先在隔离副本里做，验证后
   只提升胜者。出现在：best-of-N worker、递归子任务、A/B worktree 对比。
2. **幂等的常态操作**：放在热路径上的维护（启动去重、回合前 checkpoint）必须
   幂等，多跑无害——否则就不能“每次都做”。
3. **fail-loud，不 fail-silent**：verify 默认 FAIL（只有明确 PASS 才算过）；
   预算耗尽**干净停**并回填未应答工具调用以保持历史合法；截断**打 trace**。
   静默的成功假象比显式失败更危险。
4. **数据/指令边界**：外部内容（文件、输出、web/MCP）永远是数据，不是指令。
5. **索引-按需-取正文**：常驻小目录 + 重内容懒加载（skills/tool_search/记忆检索）。
6. **权限即角色**：一个节点能做什么由它**拿到的工具**定义，不靠提示词恳求。
7. **收敛性**：任何“循环直到”的过程都要有上限或 dry 计数（`max_depth` /
   `max_subtasks` / `max_verify_retries` / 调度的连续失败自动停用），否则不收敛。

## 第五部分：失效模式总表

| 机制 | 失效模式 | 触发条件 | 缓解 | 残余风险 |
|---|---|---|---|---|
| 分类 | 投入错配 | 分类器保守判 Medium | Medium 有 plan+verify 兜底 | high 路径少被触发 |
| best-of-N | 选错最优 | verifier 弱（`q` 低） | verify 用更高 tier | 受 `q` 封顶 |
| 递归分解 | 成本爆炸 | 过度拆分 / 全 pro | `max_depth`/`max_subtasks` | 大任务仍可能跑不完 |
| 无工具推理 | 幻觉工具调用文本 | 工具训练模型被剥夺工具 | 提示词声明 + 容错解析 | 偶发格式漂移 |
| 渐进披露 | 该取的正文没取 | 模型判断失误 | 描述写清触发条件 | 依赖模型自觉 |
| 隔离-提升 | 拷贝过贵/失败 | 大工作区 | 失败回退真实工作区 | 大仓库 `-o` 慢 |
| 沙箱（Windows） | 非内核隔离 | 恶意子进程 | 策略级路径门控 + 审批 | 不是强隔离 |

## 第六部分：诚实的边界 —— 这套设计**不**解决什么

- **不抬推理天花板**：plan/verify 跑在主模型上，编排产物质量 ≤ 主模型判断力。
- **verify 弱时会放行错误**：best-of-N 的上限是 verifier 精度 `q`。
- **分类器保守**：很多本该 High 的任务被判 Medium，递归路径在实践中触发不多。
- **全 pro 时结构负 ROI**：没配 `fast_model` 时，多跑/分治是纯成本。
- **Windows 沙箱是策略级**：路径与可写根门控，不是内核隔离；MCP/hook 跑在沙箱外。
- **度量是弱信号**：N 小、在噪声内时不能断言对其他 agent 的优势。

把这些写进文档本身，就是这套设计哲学的一部分：**宁可显式标出边界，也不制造
“全都解决了”的假象**（这正是不变量 3 的延伸）。

## 附录 A：量化速查

- best-of-N（完美 verify）：`P = 1 − (1−p)^N`；不完美：`P ≈ q·(1−(1−p)^N)`。
- 重试：`1 − (1−P)^(R+1)`。
- 递归调用量级：`(S·(N+2))^d`。
- 缓存：命中输入 token ≈ 未命中的 1/120（README 自述）。

## 附录 B：调参旋钮

| 旋钮 | 作用 | 默认 | 经济学含义 |
|---|---|---|---|
| `workers` | Medium best-of-N 数 | 2 | N，边际递减 |
| `high_workers` | High 单次 best-of-N 数 | 3 | 同上，难任务多给一点 |
| `max_verify_retries` | 闭环重试上限 | 1 | R，每轮全价 |
| `max_depth` | 递归深度上限（0=关） | 1 | 限指数 |
| `max_subtasks` | 单次分解子任务上限 | 6 | 限分支因子 S |
| `fast_model` | 便宜 tier；空则回退主模型 | 空 | 决定结构 ROI 的符号 |
| `vl_*` | 视觉后端；缺省回退主端点 | 空 | — |

## 一页纸总览

```
约束                         → 推论                    → 机制
─────────────────────────────────────────────────────────────────
模型是瓶颈                    → 框架只抬下限            → 分层编排 / best-of-N
调用非确定                    → 重复+复核才可信         → repeats / verify / 闭环
上下文稀缺                    → 默认少给、按需取        → 渐进披露 / 上下文编辑
强模型越权勤奋                → 权限即角色              → 无工具推理节点
外部内容不可信                → 数据≠指令              → 沙箱 × 审批 / hooks

不变量：隔离-提升 · 幂等 · fail-loud · 数据/指令边界 · 索引-按需 · 权限即角色 · 收敛性
经济学：结构 ROI > 0 ⟺ 便宜 tier 够便宜 且 verify 够强
边界：不抬天花板；verify 是上限；全 pro 时负 ROI；策略级沙箱
```

## 第七部分：从一次用户请求到一次可回滚落地

前文讲的是理念与约束；这一节把它们压成**一条运行时路径**。因为一个系统是否“真的长成了文档里说的样子”，最终要看：一条真实请求流过时，约束有没有在关键节点被兑现。

### 7.1 热路径分镜

一次典型请求在 Rust 线里大致经过下面几层：

1. **CLI / GUI 收到用户输入**
   - CLI 入口在 `rust/crates/ncx-cli/src/main.rs`
   - GUI 入口是 Tauri + Svelte：`rust/gui/src-tauri/src/lib.rs` 与 `rust/gui/src/App.svelte`
2. **加载配置与项目上下文**
   - `ncx-config` 负责把 CLI flags、环境变量、用户配置合并成一个 resolved config
   - 项目说明、skills 索引、memory recall 在 session 启动时被拼成 system prompt 的“起始视图”
3. **构造 ToolContext / ToolRegistry**
   - 这一步把 sandbox、approval、timeout、hooks、memory、search、skills 挂到真正执行动作的边界上
4. **进入 AgentLoop**
   - 模型拿到当前对话和当前可见工具 schema
   - 产生文本或工具调用
5. **工具执行**
   - 所有动作都经过 `ToolRegistry::execute`
   - `pre_tool` / `post_tool` hooks 在这里挂钩
   - shell / patch 再向下经过 policy executor 与 approval classifier
6. **session 记录与上下文编辑**
   - 本地历史完整保存
   - 发送给 provider 的视图则可能被压缩、裁剪、折叠
7. **回合结束**
   - 成功就把结果留在工作区
   - 失败也尽量留下可审计轨迹
   - 下一轮继续，直到 stop condition 命中

这里最重要的不是“有几层”，而是**每层都在兑现不同的不变量**：

- 配置层兑现“收敛性”和“可控性”
- ToolContext 层兑现“动作边界单点收口”
- approval/sandbox 层兑现“数据/指令边界”
- context edit 层兑现“索引-按需-取正文”
- checkpoint 层兑现“隔离之后再落地”

### 7.2 为什么 checkpoint 是热路径的一部分，而不是附加功能

`rust/crates/ncx-core/src/checkpoint.rs` 把 checkpoint 放在一个很“土”的层次上：它不是精细事务，不追求字节级增量，不尝试解释 patch 语义，而是直接做**工作区快照**。

这背后的哲学很直接：

- agent 的修改不是 IDE 单步编辑，而是“模型 + 工具 + shell”混合动作；
- 一旦允许 shell，理论上的状态空间远大于“只改几个文本文件”；
- 所以可逆性不能建立在“我猜它改了什么”，而要建立在“我事先保存了什么”。

于是 checkpoint 设计故意选了几个非常保守的特征：

- **在 Git 之外保存**：不污染提交历史，也不依赖用户先 clean commit。
- **限制文件数 / 总大小 / 单文件大小**：防止快照本身变成新的失控源。
- **恢复前先做 safety checkpoint**：回滚动作自己也可回滚。
- **排除 `.git`、`target`、`node_modules` 等目录**：避免把大量可再生工件当作核心状态。

这不是“最优雅”的回滚方案，但它符合本项目一直坚持的原则：**先要一个失败时也能工作的机制，再谈更聪明的机制。**

### 7.3 “完整本地历史 + 发送时编辑视图”为什么比“直接删历史”更关键

很多 agent 系统在上下文过长时，会真的修改历史，把旧内容摘要掉甚至覆盖掉。nanocodex 在 Rust 线里坚持了另一种策略：

- **本地 session 历史保持完整**
- **provider 看到的是 send-time edited view**

这看起来像一个工程实现细节，实际上是一个哲学选择：

- 如果本地历史也被改写，你就失去了审计能力；
- 如果只编辑发送视图，系统还能同时保有两种现实：
  - 对模型来说：上下文足够短，成本可控；
  - 对人和系统来说：原始轨迹仍然存在，可追责、可复盘、可调试。

这正是“不把运行时优化伪装成事实修改”的体现。**优化只能改变模型看到什么，不能悄悄改变系统真正发生过什么。**

## 第八部分：运行时角色学 —— 不是多 agent，而是多职责

外部看 nanocodex 很容易把它概括为“有 orchestrator、worker、verifier，所以它是 multi-agent”。这说法不算错，但还不够精确。更准确地说，它是一个**职责被拆开的单系统**。

### 8.1 分类器不是“小模型版经理”，而是预算开关

`orchestrator.rs` 里的 classify 节点只回答一个问题：**这件事值不值得花更多结构成本？**

它不是为了理解全部任务，而是为了把任务送进不同的成本曲线：

- `Simple`：直接做，少一层结构税
- `Medium`：加上计划与复核
- `High`：允许分解，但把指数爆炸锁在上限里

所以分类器的职责不是真理判断，而是**预算路由**。这也是为什么分类不清时默认 `Medium`：因为 `Medium` 是最稳妥的中间挡，既不过度昂贵，也不至于完全裸奔。

### 8.2 planner 不是“写 TODO list”，而是固定 worker 的搜索空间

计划节点真正的作用不是好看，而是减少 worker 每次都从零开始搜解空间。

如果没有 plan，best-of-N 的多个 worker 很可能只是：

- 同时犯同类错误；
- 在不同方向上无序发散；
- 给 verifier 一堆无法比较的候选。

有了一个共享 plan 后，worker 虽然仍然独立，但它们是在**同一任务坐标系**里独立。这样 verifier 才有比较基准。

换句话说，plan 不是为了替代执行，而是为了让“多个执行尝试”变得可比较。

### 8.3 verifier 不是质检装饰，而是整个结构的上限

文中前面已经给出了 `q · (1 - (1-p)^N)` 的直觉式公式。落实到工程上，verifier 之所以重要，是因为它决定了“额外花的钱到底有没有转化为可靠性”。

如果 verifier 太弱，会出现三种非常典型的问题：

1. 选错 best worker
2. 把未完成结果误判为 PASS
3. 给出模糊反馈，导致 closed loop retry 学不到可操作修正

这就是为什么 High 路径要让 verify 跑在 main tier 上，而不是跟 worker 用同级 cheap model。**worker 负责撒网，verifier 负责收网；收网的人弱，撒再多网也没意义。**

### 8.4 memory 不是外挂知识库，而是项目驯化层

`memory.rs` 的开头已经写得很直白：memory 不是涨 IQ，而是积累“经过验证的项目经验”。

它的设计边界非常克制：

- 只记录 verified notes
- 只存人类可读 markdown
- 只做轻量 lexical-semantic 排序
- 默认把 recall 当作 **leads**，不是不可质疑的 facts

这说明 memory 在这个系统里的角色不是“第二个大脑”，而是**项目磨合层**：

- 第一次做某件事时，靠模型 + 工具
- 第二次再做类似事时，memory 提醒“上次这里踩过坑”

这是一种很务实的“变熟练”，而不是浪漫化的“自我进化”。

### 8.5 tool_search / skill 不是锦上添花，而是上下文配给制度

`tools.rs` 明确把 `tool_search` 和 `skill` 做成一级公民，这很关键。它们不是为了“功能更多”，而是为了把上下文从“全量福利制”改成“按需配给制”。

系统默认不把一切正文塞进去，而是先给：

- 工具目录
- skill 名称与描述
- 少量 always-visible tools

只有当模型显式表现出需要时，才进一步暴露正文。这说明本系统把上下文当作**预算**而不是免费缓存。谁值得常驻，谁应该懒加载，是架构层决定的，不是临时 prompt 小技巧。

## 第九部分：几条很少被写进文档、但决定体验上限的“冷设计”

有些机制不会出现在宣传页 headline 上，但它们往往最能决定一个 agent 在真实使用里“顺不顺手”。

### 9.1 fail-loud 不是更保守，而是更尊重用户时间

`verdict_passed()` 的实现是一个非常典型的选择：**只要显式包含 FAIL 才算失败**，而不是要求模型必须严格输出某种格式才能继续。

表面看这像一个 parser 容错细节，实际上是两层取舍：

- 对模型输出格式：宽容，避免因为格式漂移把可用结果全丢掉；
- 对任务完成判断：保守，只要 reviewer 明确说 FAIL 就必须回路修正。

对应到用户体验，就是：

- 少因为格式问题卡死
- 多因为真实风险停下来

这是一种把“严格”放在真正重要位置上的设计，而不是到处平均用力。

### 9.2 幂等维护动作适合放在启动时，昂贵维护动作必须显式触发

memory consolidation 的“两档机制”特别有代表性：

- 启动时：轻量、幂等、便宜的 heuristic consolidate
- 显式命令：昂贵、模型参与的 summarize_consolidate

为什么这条分界这么重要？因为 agent 的热路径最怕两件事：

1. 每次启动都偷偷烧钱
2. 每次启动都引入新的随机性

把昂贵维护动作移出热路径，本质上是在捍卫一个原则：**使用主路径应该尽量稳定、便宜、可预期；高阶整理是 maintenance，不是默认税。**

### 9.3 审批状态机不是“安全附属品”，而是交互协议

`approval.rs` 看起来像安全模块，但它同时也是交互模块。因为它定义了系统与用户在“要不要冒险继续”这件事上的协议。

四种 policy 本质上是四种协作风格：

- `untrusted`：默认不信，适合陌生仓库或高风险环境
- `on-failure`：先在沙箱里试，失败再问
- `on-request`：模型可以主动请求升级
- `never`：严格禁止升级，宁可任务失败

这说明 approval policy 不是纯安全配置，而是**风险偏好接口**。它把“系统该多自主”这个原本含糊的问题，压成了有限、可解释、可切换的几种模式。

### 9.4 GUI 的价值不是“有个窗口”，而是把可见性前移

Tauri GUI 与 Python GUI 虽然技术栈不同，但共同点很清楚：它们不是只给 CLI 套个壳，而是在把系统内部状态尽量外显：

- tool_start / tool_result
- approval modal
- settings 与 config path
- checkpoints panel
- busy / done / error 状态

对 agent 来说，很多焦虑都来自“它现在到底在干嘛”。GUI 做的不是把命令点按钮化，而是把不可见的中间态拉到前台。**可见性本身就是可靠性的组成部分。**

## 第十部分：如果把 nanocodex 看成一部“少年漫画”，主角其实不是模型

为了避免文档最后只剩抽象名词，我们用一个故意轻松但很准确的比喻收尾。

如果把整个系统画成一部战斗漫画：

- **模型**不是全知主角，而是火力最强但也最容易上头的战斗员；
- **orchestrator** 像战术指挥，不负责亲自砍人，只负责决定什么时候该群殴、什么时候该单挑；
- **sandbox / approval** 像结界与队规，保证战斗再激烈也别把自家基地炸了；
- **memory** 像前辈留下的作战笔记，不给你超能力，只减少“同一个坑摔两次”；
- **checkpoint** 像战斗前存档点，打输了能回村，不用删号重练；
- **tool_search / skills** 像兵装库目录，不是把所有武器绑身上，而是先看目录，再按需取刀。

于是这套系统真正的主角不是“某一个最聪明的节点”，而是那几条贯穿始终的不变量：

- 先隔离，再提升
- 默认少给，按需展开
- 失败要大声，成功别假装
- 权限决定角色，不靠口头约定
- 把昂贵能力放在真正值钱的位置上

把这些不变量守住，模型换代、GUI 换代、provider 换代、甚至语言从 Python 换到 Rust，系统的性格仍然是连续的。**这比任何单个 feature 更接近“设计哲学”真正该写的东西。**
