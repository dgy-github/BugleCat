# 智能复利验证实验：真实仓库 Issue 时序回放（设计稿 v0）

> 状态：草案，待确认后再写代码。
> 预算约束：**每轮 ≤ 2 元**，一轮 = 一个对照组按时间顺序跑完一份 curriculum。

## 1. 研究问题与假设

- **问题**：agent 能否依靠自身积累的经验，在后续任务上持续变强？收益来自哪个机制？
- **H1（复利存在）**：在同一组按时间排序的 issue 上，B 组（完整复利机制）后半段的通过率高于 A 组（无记忆），或单任务成本低于 A 组。
- **H2（来自顺序积累）**：把 B 组的任务顺序打乱（D 组）后，后半段优势缩小。
- **H3（可迁移）**：B 组积累的记忆冻结后，迁移到 holdout 任务上依然优于 A 组。
- **H0（证伪条件）**：3 次重复后，B 与 A 的差异落在 A 自身的重复方差以内，则判定"当前机制没有复利"。这也是有效结论。

## 2. 任务构造（SWE-bench 式）

每个任务由一个"issue + 修复 PR"组成：

| 字段 | 来源 |
|---|---|
| `base_commit` | 修复 PR 合并前的父提交 |
| `problem` | issue 标题 + 正文（不含任何讨论中给出的补丁） |
| `fail_to_pass` | 修复 PR 新增或修改、修复前失败、修复后通过的测试 |
| `pass_to_pass` | 修复前后都通过的相关测试（防止改坏） |
| `created_at` | issue 创建时间，用作回放顺序 |

筛选条件：
- 修复只涉及少数几个源文件，并且修复 PR 自带测试；
- 在 `base_commit` 上能用固定的 Python 版本和依赖装好环境；
- 排除纯文档、纯 CI、纯依赖升级。

Curriculum 规模：**主序列 12 个 + holdout 6 个**，都取自同一仓库。holdout 任务在时间上与主序列交错，但不参与记忆积累。

## 3. 候选仓库（待逐个核实）

选择标准：纯 Python、体积小、pytest 齐全，而且**同类问题反复出现**，否则没有可复用的经验。

| 候选 | 理由 | 风险 |
|---|---|---|
| `andialbrecht/sqlparse` | 单包、lexer / 格式化类 bug 大量同构，很适合复利 | 部分老 issue 没有配套测试 |
| `python-poetry/tomlkit` | 解析 / 保格式写回类边界 bug 多且相似 | 部分修复跨多个文件 |
| `arrow-py/arrow` | 日期解析 / 本地化问题反复出现 | 时区依赖可能导致测试不稳定 |
| `more-itertools/more-itertools` | 极小、测试快 | issue 多为新功能，同构 bug 少 |
| `pyparsing/pyparsing` | 历史长、同类问题多 | 单文件很大，读代码 token 成本高 |

初步倾向是 **sqlparse**，下一步先核实可用任务数。

## 4. 对照组

| 组 | 配置 | 目的 |
|---|---|---|
| A | 关闭所有记忆（提取、召回、降权、晋升） | 基线 |
| B | 完整复利机制 | 检验 H1 |
| D | 与 B 相同，但任务顺序随机打乱 | 检验 H2 |
| C* | 消融：逐项关闭单个机制 | 定位收益来源（等 H1 成立后再做） |

控制变量：同一模型版本、temperature、系统提示、工具集；每组从**空记忆库**开始；各任务之间工作区完全重置，只有记忆库跨任务保留。

## 5. 指标

- **主指标**：按任务序号画 `fail_to_pass` 全部通过的二值曲线；比较前 6 个与后 6 个任务的通过率差（B − A）。
- **次指标**：单任务 token、轮数、金额；`pass_to_pass` 回归率。
- **记忆诊断**：每个任务召回了哪些记忆、这些记忆来自哪个先前任务、召回后是否被实际使用。这部分用来解释"为什么有或没有复利"。

## 6. 预算与硬上限

DeepSeek 估算单任务约 0.15 元（价格以官网为准）：

- 单任务上限：**150k 输入 token、15 轮、0.18 元**，超过任一项即判失败并停止；
- 每轮 12 个任务 × 0.15 元 ≈ 1.8 元，留出余量，总额 ≤ 2 元；
- holdout 只在 H1 初步成立后跑，单独计为一轮；
- runner 每轮实时累计金额，超过 2 元立即中止。

第一阶段总花费估计：A、B 各 3 次重复 = 6 轮 ≈ 12 元。

## 7. 实施步骤（确认后执行）

1. **任务挖掘脚本**（不花 API 费）：拉取候选仓库的 issue 和 PR，自动筛选出候选任务；在本地验证每个任务的 `fail_to_pass` 在修复前失败、修复后通过，产出 `tasks.jsonl`。
2. **回放 runner**：按时间顺序对每个任务执行"重置工作区 → 调用 ncx → 跑裁判测试 → 记录指标"，记忆库目录按组隔离。
3. **记忆开关**：保证 A/B/C 所需的每个机制都能通过配置单独开关；不足的部分补齐。
4. **报告**：学习曲线、组间差异、方差、记忆溯源。
5. 冒烟：先用 2 个任务跑通全流程（约 0.3 元），再正式开跑。
