# 作用域 Agent 与云→端蒸馏 — 设计文档 v0.1

> 状态：设计稿，待评审。日期：2026-11-04。
> 一句话：给每个 agent 定义书面**作用域**，用云端算力把该作用域里**稳定的工作方式**蒸馏成本地小模型的 LoRA 权重，让离线模型在作用域内独立完成固定模式的工作；越界的任务交回云端大模型或人。

## 0. 结论先行

- 作用域是整个方案的地基。训练数据按作用域归档，评测按作用域验收，运行时按作用域限权，越界按作用域交接。
- **进权重的只有"怎么做"**（流程、格式、判断习惯、工具调用方式）。会变的事实和私有数据内容放记忆/检索，硬约束放运行框架（沙箱、审批）。
- 分三级推进：先用零权重办法（ncx-forge 优化提示词 + 记忆）把效果做到上限，再上 LoRA 微调，最后才考虑偏好/强化学习。
- 现有仓库已有一半零件（`train/` 的 forge、SFT 数据构建、ACR 统计、Jev 执行前审查、AppContainer 沙箱）。缺的是：作用域清单、从真实会话导出训练样本、脱敏、本地部署链路和离线评测门槛。

## 1. 目标与非目标

**目标**

1. 用户能为一类固定工作定义一个作用域 agent，例如"售后退款处理""周报生成""订单对账"。
2. 云端算力负责提炼、合成数据和训练；训练出的 LoRA 下发到本地，离线运行。
3. 本地 agent 在作用域内的结果可验证，达到合格线才上线，退化可回滚。
4. 越界任务被识别并交接，不靠模型自觉。

**非目标（本版不做）**

- 不追求通用离线助手。小模型能力有上限，只做窄、固定、可验证的流程。
- 不把私有事实（客户、价格、项目状态）写进权重。
- 不改 agent 核心循环、沙箱实现和工具实现；只新增作用域层和训练/部署管道。

## 2. 核心概念：作用域（Scope）

### 2.1 作用域包含的六类边界

| 边界 | 内容 | 运行时由谁执行 |
|---|---|---|
| 职责 | 接哪类任务、输入输出契约 | 路由器（§3）+ Jev 作用域检查（§8） |
| 数据 | 可读的数据源、记忆命名空间 | 沙箱可读根、记忆存储隔离 |
| 工具与权限 | 允许的工具、可写目录、网络、审批规则 | 工具注册表过滤、`SandboxPolicy`、权限模式 |
| 模型 | 底座模型 + LoRA 适配器版本 | 本地推理端点 |
| 验收 | 固定评测任务集、合格线 | 离线评测门槛（§7） |
| 越界处理 | 超出作用域时交给谁 | 路由器降级到云端或人工 |

### 2.2 作用域清单格式

每个作用域一份 TOML，放在工作区 `agents/<id>.toml`（项目级）或 `~/.nanocodex/agents/<id>.toml`（用户级）。示例：

```toml
schema = "ncx-scope/v1"
id = "refund"
name = "售后退款处理"
version = 3

[duty]
summary = "处理退款工单：核对订单与规则，给出结论和回复草稿"
accepts = ["退款", "退货", "refund"]          # 路由关键词，辅助分类器
input = "一张退款工单（订单号、诉求、聊天记录）"
output = "结论（同意/拒绝/转人工）+ 依据 + 回复草稿"

[data]
read_roots = ["data/orders", "docs/refund-policy"]
memory_namespace = "refund"                     # 只读写这一块记忆

[tools]
allow = ["read_file", "grep", "shell", "apply_patch"]
deny = ["web_fetch"]
writable_roots = ["out/refund"]
network = false
os_sandbox = "enforce"

[[tools.approval]]                              # 需要人工审批的情形
when = "refund_amount > 500"
reason = "大额退款"

[model]
base = "qwen3-8b-instruct-q4_k_m.gguf"
adapter = "refund-v3"                           # 空 = 只用底座 + 提示词
endpoint = "http://127.0.0.1:8080/v1"           # 本地 OpenAI 兼容端点
fallback = "preset:deepseek/deepseek-v4-pro"    # 越界或失败时交给云端

[acceptance]
suite = "agents/refund/acceptance.jsonl"        # 固定验收任务集
pass_rate = 0.95
no_regression = true                            # 新版本不得低于当前版本

[escalation]
on_out_of_scope = "fallback"                    # fallback | human | refuse
on_low_confidence = "human"
```

### 2.3 作用域的不变式

- 作用域只能**收窄**权限，不能放宽全局策略。全局是 `read-only`，作用域不能开写。
- 作用域文件本身属于受保护路径：agent 运行时不可写（复用 AppContainer 受保护路径机制，见 `os_isolation.rs` 的 `protected_paths`）。
- 版本号单调递增；适配器、验收集、清单三者一起打版本，回滚时一起回滚。

## 3. 总体架构

```text
            ┌──────────────┐  不匹配/低置信  ┌──────────────────┐
 任务 ───▶  │   路由器      │ ─────────────▶ │ 云端大模型 / 人工  │
            │ (作用域分类)   │                └────────┬─────────┘
            └──────┬───────┘                         │ 产生新轨迹
                   │ 命中作用域 X                      ▼
                   ▼                           ┌──────────────┐
          ┌─────────────────┐   轨迹 + 结果     │  轨迹归档     │
          │ 本地 agent X     │ ───────────────▶ │ (按作用域)    │
          │ 底座 + LoRA-X    │                  └──────┬───────┘
          │ 作用域限权运行    │                         │ 脱敏 → 筛选
          └─────────────────┘                         ▼
                   ▲                           ┌──────────────┐
                   │ 通过验收才下发              │ 云端教师 +    │
                   └──────────────────────────  │ 云端 GPU 训练 │
                                               └──────────────┘
```

- **路由器**：先用清单里的 `accepts` 关键词和任务描述做轻量分类，再让本地 agent 自检"是否在职责内"。两者都通过才执行。
- **云端**只出现在两处：处理越界任务，和离线的提炼/训练。在线执行作用域任务时不依赖云端。

## 4. 数据管道

1. **采集**：会话已经落在线程存储（`~/.nanocodex/threads-v2.json`）里，含工具调用和结果。新增字段：每轮记录命中的作用域 id 和版本。
2. **归档**：按作用域把轮次导出为 `ncx-scope-trajectory/v1` JSONL，结构沿用 `train/export.py` 的 `ncx-forge-trajectory/v1`（system_prompt、messages、reward），增加 `scope`、`scope_version`。
3. **筛选（什么算成功）**：
   - 复用 ACR 口径（`docs/intelligence-compounding-feedback-plan.zh-CN.md`）：只取 **ACR-strict** 无人工介入的 Primary 任务；
   - 加上作用域验收：任务有可执行检查的，检查通过才算；
   - 用户事后改正、撤销、差评的轮次一律剔除。
4. **脱敏**：在本地完成，再上传。规则按作用域配置（订单号、手机号、姓名、金额区间化等），脱敏后做一次泄露扫描，命中则整条丢弃。
5. **提炼与合成**：云端教师模型做三件事：
   - 把成功轨迹改写成干净的示范（去掉走弯路的步骤，保留判断依据）；
   - 根据作用域职责生成**合成任务**，补齐少见情形；
   - 给失败轨迹写"正确做法"，作为偏好数据的正例。
6. **数据集切分**：train / val / test 按时间切，test 冻结不参与任何训练与提示词优化，防止过拟合（沿用 forge 的切分思路，`train/splits.py`）。

## 5. 训练：三级推进

| 级别 | 方法 | 改什么 | 何时进入下一级 |
|---|---|---|---|
| L0 | 零权重：ncx-forge 按作用域进化 genome（提示词、工具描述、策略参数）+ 作用域记忆种子 | 文本与参数（`NCX_GENOME` 注入） | 验收通过率在 val 上连续两轮不再提升 |
| L1 | LoRA SFT：模仿 L0 最优 genome 下的成功轨迹 | 适配器权重 | SFT 后 val 通过率提升，且收益仍未饱和 |
| L2 | 偏好 / GRPO：以验收检查为奖励 | 适配器权重 | — |

- **L1 复用** `train/finetune.py`：`build_sft_dataset`（只取 reward==1）和 `run_sft`（TRL `SFTTrainer`）已有，需改成 LoRA（PEFT）并按作用域输出适配器。
- **L2 复用** `rl_design()` 写好的契约：episode = 在新工作区跑一轮作用域任务，reward = 验收检查 0/1，按任务分组算 GRPO 优势。需要补 agentic rollout 采集器。
- **一个作用域一个适配器**，共用一个底座。适配器小（通常几十 MB），便于分发和回滚。
- 训练在云端 GPU 上进行，产物只有适配器和训练报告；训练数据用完即删（见 §9）。

## 6. 部署

1. 适配器合并或以 LoRA 形式量化为 GGUF，由本地 llama.cpp / LM Studio 类服务加载，多适配器按请求切换。
2. 本地服务暴露 OpenAI 兼容端点，BugleCat 现有自定义供应商机制可直接接入（清单 `model.endpoint`）。
3. 版本目录：`~/.nanocodex/agents/<id>/v<N>/{adapter.gguf, manifest.toml, report.json}`，`current` 指向在用版本；回滚只改指针。
4. 下发前校验适配器哈希和底座匹配，不匹配拒绝加载。

## 7. 离线评测门槛

- 每个作用域的验收集（`acceptance.suite`）是唯一上线标准：
  - 通过率 ≥ `pass_rate`；
  - `no_regression = true` 时，不得低于当前在用版本；
  - 越界样本（故意放入的不属于本作用域的任务）必须被拒绝或交接，误接即不合格。
- 评测在本地离线跑，与线上同一份底座和权限配置。
- 上线后持续统计该作用域的 ACR-strict；连续低于阈值自动降级：先回滚到上一版本，仍不达标则整体走 `fallback`。

## 8. 运行时作用域执行

| 清单字段 | 映射到现有机制 |
|---|---|
| `tools.allow / deny` | 工具注册表过滤（只把允许的工具 schema 给模型） |
| `tools.writable_roots`、`data.read_roots`、`network` | `SandboxPolicy` 可写根 / 网络开关；`os_sandbox = "enforce"` 时由 AppContainer 强制 |
| `tools.approval` | 审批策略（命中条件时强制 Ask） |
| `data.memory_namespace` | 记忆存储按命名空间隔离 |
| 职责 + 越界 | Jev 执行前审查 `exceeds_scope` |

**Jev 的改动**：现在 `exceeds_scope` 的判断依据只有 `user_requests`（见 `verification/action_review.rs` 的 `questions()`）。改为同时提供作用域清单的职责与边界摘要，判定"该动作是否超出 `user_requests` **或作用域**"。作用域内的确定性规则（不在 `allow` 里的工具、可写根之外的路径）在 Jev 之前就由注册表和沙箱硬拦，Jev 只负责语义层面的越界。

## 9. 隐私与安全

- **三种上云模式**，按作用域选择：
  1. 仅上传脱敏后的轨迹（默认）；
  2. 只上传作用域描述和少量示例，由云端教师生成合成数据，原始轨迹不出本机；
  3. 训练放在用户自有或机密计算 GPU 上，原始数据可用，训练结束即销毁。
- **事实不进权重**：权重无法定点删除，个人信息和业务事实一旦进入权重就无法撤回，所以只放记忆/检索，可随时删除。
- 训练报告记录：用了哪些轨迹（哈希）、脱敏规则版本、教师模型、数据保留与销毁时间。
- 本地适配器与清单受 AppContainer 受保护路径保护，agent 自身无法改写自己的作用域或权重。

## 10. 与现有代码的对应

| 需要的能力 | 现有零件 | 状态 |
|---|---|---|
| 零权重进化 | `train/forge.py`、`genome.py`、`NCX_GENOME` 注入 | 可用，需按作用域分 genome |
| 轨迹导出 | `train/export.py` | 只覆盖 bench 任务，**需新增**从线程存储按作用域导出 |
| SFT 数据与训练 | `train/finetune.py`（`build_sft_dataset`、`run_sft`） | 可用，需改 LoRA + 按作用域输出 |
| 强化学习契约 | `train/finetune.py` 的 `rl_design()` | 只有契约，需补 rollout 采集器 |
| 成功判定 | ACR / `TaskOutcome`（intelligence-compounding 计划） | 可用 |
| 越界审查 | Jev `exceeds_scope` | 可用，需接入作用域 |
| 运行限权 | `SandboxPolicy`、权限模式、AppContainer、受保护路径 | 可用 |
| 本地模型接入 | OpenAI 兼容自定义供应商 | 可用 |
| 作用域清单、路由器、脱敏、适配器部署与回滚、离线评测门槛 | — | **需新增** |

## 11. 分阶段路线图

| 阶段 | 内容 | 完成标准 |
|---|---|---|
| M0 | 作用域清单格式与加载；运行时按清单限权（工具、沙箱、审批、记忆命名空间） | 一个示例作用域在本地跑通，越权动作被拦 |
| M1 | 线程存储按作用域导出 + 本地脱敏 + 泄露扫描；验收集格式与离线评测器 | 一个真实作用域攒到 ≥200 条通过筛选的轨迹，评测器能出通过率 |
| M2 | L0：forge 按作用域进化 genome | val 通过率较初始提升并饱和 |
| M3 | L1：云端 LoRA SFT → GGUF → 本地加载；版本目录与回滚；上线门槛 | 本地离线模型在 test 上达到合格线，且不低于云端基线的约定比例 |
| M4 | 路由器 + Jev 作用域检查 + 上线后 ACR 监控与自动降级；L2 视收益决定 | 一周真实使用中越界全部被交接，ACR 不低于上线时 |

## 12. 风险与开放问题

1. **底座能力上限**：小模型在长上下文和多步工具调用上明显弱。作用域要足够窄；必要时给作用域配更大的本地底座。
2. **数据量**：每个作用域至少几百条高质量轨迹才值得做 L1。冷启动期主要靠云端处理并积累数据。
3. **遗忘与干扰**：一作用域一适配器可避免互相干扰，但底座升级时所有适配器需重训。
4. **路由误判**：误把越界任务派给本地 agent 的代价最高。验收集里必须包含越界样本；低置信一律交接。
5. **评测集老化**：业务规则变化后，验收集要跟着更新，否则门槛失真。需要规定谁维护、多久复核。
6. **开放问题**：
   - 作用域清单由用户手写，还是由云端根据历史会话自动起草、用户确认？
   - 多个作用域协作（一个任务跨作用域）时，由路由器拆分，还是交给编排器（orchestrator）？
   - 合成数据占比上限多少，才不会让模型学到"教师的习惯"而不是"用户的习惯"？
