# 智能售后系统 · 多智能体架构设计文档

> 版本 v0.1 · 2026-06-30
> 场景:茶饮/餐饮连锁(茶百道)跨外卖平台的智能售后与协同处理

---

## 1. 背景与目标

在**美团、饿了么、京东**外卖平台,以及**自有小程序**等多个来源上,围绕餐饮质量与售后反馈,构建一套**接入后台售后系统**的智能处理平台。

核心目标:

- 多来源统一接入,自动分诊(投诉 / 退款 / 催单 / 举报等)。
- 尽量**自助闭环**,无法闭环时按规则升级到智能客服 / 人工客服 / 门店 / 总部。
- 支持门店侧多种处理方式:**退款、补单、赔偿**。
- 覆盖供应链侧:缺货、补货、店员反馈。
- 具备**举报机制**与异常识别(风控)。
- 以**多智能体协同**承载"需要推理和协商"的部分。

---

## 2. 核心设计判断:薄 Agent + 厚工作流

**本系统适合多智能体,但不是"全都做成智能体"。**

系统中很大一部分本质是**确定性路由 + 状态机**,如果硬套 agent,会导致:结果不可复现、成本高、难以排障。

设计原则:**用少量职责清晰的 agent 承载"需要推理与协商"的部分,其余用状态机 / 规则 / 工具调用兜底。**

### 2.1 哪些是"路由",哪些才是"智能体"

| 环节 | 本质 | 实现方式 |
|---|---|---|
| 平台来源识别(美团/饿了么/京东/小程序) | 打标签 | 规则 / 适配器 —— **不是** agent |
| 投诉 vs 退款 → 不同入口 | 分支 | 意图分类(一次 LLM 调用)+ 状态机 |
| 总部 → 对应订单门店 的转接 | 查订单映射 | 确定性查表 —— **不是** agent |
| 退款 / 补单 / 赔偿 的最终执行 | 写业务系统 | 工具调用 + 审批 —— **不是** agent |
| 缺货 → 补货、举报 | 工单流转 | 工作流引擎 |

> 判据:多智能体的价值不在"流程分叉多",而在**每个角色需要独立推理、调工具,并可能互相协商**。

---

## 3. Agent 拆分

按"一张售后单"的主线,建议 **4~5 个 agent**:

### 3.1 接待 / 分诊 Agent(Triage)
- **唯一直接对接用户**的入口。
- 职责:理解自然语言诉求、判定投诉/退款/催单/举报、抽取订单号、判断"能否自助闭环 or 必须转人工"。
- 最需要 LLM 能力的角色。

### 3.2 售后决策 Agent(门店侧)
- 输入:订单 + 证据(照片、金额、历史)。
- 职责:在 **退款 / 补单 / 赔偿** 之间给出方案与额度,受策略与权限约束。

### 3.3 客服协同 Agent
- 智能客服兜底。
- 职责:判断何时升级到人工(信心低、金额大、情绪激烈)。

### 3.4 供应链 Agent
- 职责:处理缺货 / 补货 / 店员反馈。
- 与售后决策 Agent 交互:**缺货会影响"能否补单"**。

### 3.5 风控 / 举报 Agent
- 职责:举报机制、异常退款识别(羊毛党、门店骗补)。
- 天然需要跨单看全局,适合独立 agent。

---

## 4. 为什么该场景适合多智能体

- **多来源、多主体、诉求异构** —— 非单一线性任务,涉及 用户 / 门店 / 总部 / 风控 多方,符合 agent 各司其职。
- **需要跨角色协商** —— 例:
  - 补单 depends 供应链是否缺货;
  - 赔偿额度 depends 风控是否判定异常。
  - 这种"决策互相牵制"是多 agent 的典型收益点。
- **人机混合** —— 智能客服 ↔ 人工客服 的升级/降级,天然是 agent + human-in-the-loop。

---

## 5. 工程红线(必须守住)

1. **金额 / 退款 / 赔偿的最终动作必须走审批**,不能让 agent 直接写库。
2. **确定性的路由不要交给 LLM**,否则同一个投诉两次路由结果不同,无法排障。
3. **每个 agent 边界要能单测**,输入 → 输出可回放。

---

## 6. 典型流转(示意)

```
用户诉求(美团/饿了么/京东/小程序)
        │
        ▼
 [来源适配器]  ── 打标签(平台、订单号)
        │
        ▼
 接待/分诊 Agent  ── 意图分类:投诉 / 退款 / 催单 / 举报
        │
   ┌────┴───────────────┬──────────────┬───────────────┐
   ▼                    ▼              ▼               ▼
 自助闭环          售后决策 Agent    风控/举报 Agent   供应链 Agent
 (状态机)          (门店侧)          (跨单)            (缺货/补货)
                       │  ▲              │                │
                       │  └──── 协商 ────┴────────────────┘
                       ▼
                 [审批网关] ── 退款 / 补单 / 赔偿
                       │
                       ▼
                 写入业务系统 + 通知用户/门店
```

协商点(agent 之间):
- 售后决策 ↔ 供应链:补单前确认库存。
- 售后决策 ↔ 风控:赔偿/退款前确认是否异常。
- 客服协同:任一环节信心不足 → 升级人工。

---

## 7. 结论

**适合,但要"薄 Agent + 厚工作流"。**

用 4~5 个有明确职责的 agent 承载"需要推理和协商"的部分(分诊、售后决策、客服协同、供应链、风控),其余环节(来源识别、订单映射、最终执行)用状态机 / 规则 / 工具调用 + 审批兜底。
