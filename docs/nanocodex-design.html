nanocodex — Design & Architecture

A from-scratch, single-binary coding agent in Rust (an OpenAI-compatible LLM loop with sandboxed tools), plus ncx-forge, a framework that evolves the agent's own harness against a verifiable benchmark. This reference walks each subsystem: how it works, why it's built that way, and the talking points behind each decision.

◆Architecture & mind-map

One turn = call-model ↔ run-tools under a sandbox; an optional orchestrator wraps it; ncx-forge is an offline meta-loop that evolves the agent's own prompt/tool-descriptions against a benchmark.

Runtime & training meta-loop

Subsystem mind-map

1The Harness — Agent Turn Loop

A single-threaded, ?Send agent turn loop (AgentLoop) that alternates call-model / run-tools — batching consecutive read-only tool calls concurrently, serializing writes, enforcing a model/tool-call budget, polling a cancel closure, routing image turns to a separate vision provider, and re-selecting the per-turn tool schema view from tool_search hints + lexical scoring.

How it works

AgentLoop::run_turn takes the event sink out of &mut self (to dodge a borrow conflict between the sink closure and &mut self), runs run_turn_inner, then applies the Stop hook and restores the sink. Inner: it sets use_vision_this_turn if a vision provider exists AND the user content carries an image_url block (has_image_block), fires the user_prompt hook (which can short-circuit the whole turn with stop_reason blocked), appends the user message, then iterates for iteration in 0..max_model_calls where max_model_calls = max_iterations.min(task_budget.max_model_calls.max(1)). Each iteration: checks the cancel closure; rebuilds the tool schema list via schemas_for_query(tool_query) (so tool_search hits surface next turn); prepends a synthetic system budget_note plus any prompt-hook output; calls call_model, which first builds a non-destructive context-edited message view (Session::for_model_edited) then dispatches to active_provider() (vision or main). On finish_reason=="error" it returns an error TurnResult; on no tool calls it records the assistant text and returns completed; otherwise it persists the assistant message with OpenAI-shaped tool_calls and walks response.tool_calls by index. For each position it re-checks cancel and remaining tool budget, then decides parallel_run: true only when the current AND next call are both read_only per the registry — it then greedily gathers the maximal run of consecutive read-only calls (capped by remaining budget) and runs them via join_all over execute_cancellable; otherwise it runs the single (write/unknown) call serially. Results are appended in original order with add_tool_result(id, name, result). Falling out of the model-call loop yields stop_reason task_budget. The ToolRegistry::execute dispatches by name (unknown name → an error string fed back to the model), running pre/post hooks around the tool.

Design rationale — why this way

The defining constraint is #[async_trait(?Send)] on the Provider, Tool, and ApprovalHandler traits: the whole agent is built to run on a Tokio current-thread runtime so it can hold non-Send state — Rc<RefCell<…>> shared context (the plan, tool catalog, tool hints), boxed FnMut mock/closure providers in tests, and the GUI's FnMut event sink — without the Send + Sync + 'static tax that a multi-threaded runtime forces (which would push everything to Arc<Mutex<…>> and atomic refcounts). The work is I/O-bound (one in-flight model call, then a short burst of tool I/O), so multi-threading buys nothing; the read-only batch concurrency is achieved with join_all of futures on one thread, not OS threads, so Send is never needed. Read-only-only batching is the safety rationale: pure-read tools have no ordering dependency and can race freely, but a write (or unknown) tool must stay serial and in declared order so file edits and their surrounding reads observe a deterministic sequence (verified by write_between_reads_stays_serial_and_ordered). The dual budget (model calls vs tool calls) plus a self-describing budget_note injected as a system message lets the model self-pace and guarantees termination even if it loops; backfilling synthetic tool results on cancel/budget keeps the message history API-valid (every assistant tool_call must have a matching tool reply or the next request 400s). Dynamic per-turn schema selection (cap DEFAULT_VISIBLE_TOOL_LIMIT=9, always-visible core set + tool_search hints + lexical matches) keeps the prompt small and the function list focused as the tool set grows, rejecting the alternative of dumping every schema every turn.

Key mechanisms

!Send / current-thread design
#[async_trait(?Send)] on Provider/Tool/ApprovalHandler means returned futures need not be Send. This lets Box<dyn Provider>, the EventSink = Box<dyn FnMut(LoopEvent)>, and Rc<RefCell<…>> shared state live across awaits on a single-thread runtime. Rationale: I/O-bound workload + cheap Rc sharing; rejected Arc<Mutex>/Send bounds as unnecessary overhead.
call-model → run-tools iteration
run_turn_inner loops up to max_model_calls. Each pass: call_model (schemas + budget/hook system notes) → if !response.has_tool_calls() return completed; else persist assistant tool_calls and execute them, append results, loop. Falling off the end returns task_budget.
tool-call parse + dispatch
The provider crate parses raw JSON into ToolCall{id,name,arguments} (invalid/non-object arguments collapse to {}, per types.rs). The loop re-serializes them to OpenAI function shape for history, then dispatches by name through ToolRegistry::execute; an unknown name returns Error: unknown tool '<name>'. back to the model rather than crashing.
concurrent read-only batching
parallel_run triggers only when is_read_only(calls[idx]) AND is_read_only(calls[idx+1]). It greedily collects the maximal run of consecutive read-only calls (bounded by remaining_tools), runs them with futures_util::future::join_all over execute_cancellable, and zips results back in order. A non-read-only or trailing single call runs serially. Proven by read_only_calls_run_concurrently (4×300ms reads finish <800ms).
task budget (dual cap)
TaskBudget{max_model_calls:60, max_tool_calls:120} (defaults). max_model_calls caps the outer loop; before each tool/batch, remaining_tools = max_tool_calls.saturating_sub(tools_used.len()) — 0 → budget_result (stop_reason task_budget, backfill unanswered). A budget_note system message reports live usage so the model paces itself.
cancellation
run_turn takes an Option<&dyn Fn()->bool>. Checked at loop top, before each tool/batch, and after each tool. execute_cancellable tokio::select!s the tool future (biased) against a 100ms poll; if cancel flips mid-run it returns [interrupted...] and drops (cancels) the tool future. stop_interrupts_a_hanging_tool proves a pending() tool is abandoned.
vision routing
use_vision_this_turn = vision_provider.is_some() && has_image_block(user_input). active_provider() returns the vision provider for that turn only; absent a vision provider, image turns stay on the main provider. has_image_block scans the content array for a block whose type == "image_url".
dynamic per-turn schema selection
Each iteration calls schemas_for_query(tool_query). If tools.len() <= 9 all schemas are sent; otherwise the view = ALWAYS_VISIBLE_TOOLS (read_file, apply_patch, update_plan, shell, tool_search, skill) + names in ctx.tool_hints (set by the last tool_search) + top lexical matches via catalog_score, capped at the limit. tool_search populates tool_hints so a discovered tool's schema appears next turn.
non-destructive context editing
call_model runs Session::for_model_edited(notes, policy) which builds a send-time view: compresses old (tool) results beyond keep_recent_messages to max_tool_result_chars, and drops the oldest prefix (re-aligned to a user boundary) when over max_chars — without mutating session.messages. Trace prints original/edited chars + compressed/dropped counts.

★ Interview talking points
  • Why ?Send is the load-bearing decision: the agent is I/O-bound and runs on a current-thread Tokio runtime, so it can share state with Rc<RefCell> and hold FnMut/mock providers across awaits — no Send+Sync+'static, no Arc<Mutex>. Concurrency where it matters (parallel reads) is single-thread join_all, not OS threads.
  • Read-only batching is correctness-driven, not just speed: only a run of *consecutive* read-only calls is parallelized; any write or unknown tool forces serial, in-order execution so edits and the reads around them are deterministic. The batch is also clipped to the remaining tool budget.
  • Two independent budgets (model calls and tool calls) guarantee termination and are surfaced to the model as a live system budget_note, turning a hard limit into self-pacing guidance; exhaustion backfills synthetic tool replies so history stays API-valid.
  • Cancellation is cooperative and two-layered: a Fn()->bool polled at loop/tool boundaries, plus execute_cancellable's 100ms select! that can abandon a hanging tool mid-run by dropping its future (test uses future::pending).
  • Dynamic per-turn tool schema selection (cap 9, always-visible core + tool_search hints + lexical scoring) keeps the function list small as tools grow; tool_search writes into ctx.tool_hints so a discovered tool becomes visible next turn — a feedback loop between a tool's side effect and the next prompt.
  • Vision routing is per-turn and opt-in: only when a separate vision provider is configured AND the turn carries an image_url block, keeping a cheaper text model as the default.
  • Robustness of message history: unknown tool names return an error string (not a panic), context editing is a non-destructive send-time view, and cancel/budget paths backfill dangling tool_calls so the OpenAI invariant (every tool_call has a tool reply) is never violated.
Trade-offs & gotchas
  • Cancellation granularity is 100ms (the execute_cancellable poll); a tool that returns faster than the first poll cannot be interrupted, and there's no hard wall-clock timeout in the loop itself (per-tool timeouts live in the shell tool, not the harness).
  • Read-only batching keys entirely on the registry's read_only() flag; a tool mis-declared read-only (one that actually mutates) would be raced and reordered. Trust boundary is the tool author.
  • with_max_iterations overwrites task_budget.max_model_calls, and with_task_budget overwrites max_iterations; the two setters clobber each other depending on call order — the effective cap is always max_iterations.min(max_model_calls.max(1)), so a mismatched pair can silently lower the cap.
  • The tool-call budget is checked *before* each call/batch, so a parallel read-only batch is sized to fit the remaining budget but the loop never partially runs a batch beyond it — fine, but it means a single over-budget assistant turn truncates remaining calls and backfills them as 'task budget exhausted'.
  • Vision routing is all-or-nothing per turn: a turn with an image sends the *entire* edited history to the vision provider, not just the image; there's no per-message model split.
  • Tool-call argument parsing is delegated to the provider crate — invalid/non-object JSON collapses to {} there, so a malformed arguments blob silently becomes empty rather than erroring at dispatch.
  • Schema selection lexical scoring (catalog_score) is a simple substring/word match (name exact=100, name-contains=50, hay-contains=20); a capability described in synonyms the query doesn't share won't surface unless tool_search is called explicitly.

2Context Compression — Context Editing

A two-mode context editor: every model call gets a non-destructive, budget-shaped "provider view" (truncate old tool results, then drop the oldest message prefix past a char budget), while an opt-in /compact bakes that same transform into the live history and rewrites the JSONL log.

How it works

Session stores the full conversation as Vec<serde_json::Value> in OpenAI chat shape (messages), with the system prompt held separately in system. ContextEditPolicy carries four knobs: enabled, max_chars (default 120_000), keep_recent_messages (default 30), max_tool_result_chars (default 4_000). The core algorithm lives in edited_body(system_notes, policy): it clones self.messages into body, records original_chars via total_chars (chars of system + notes + every message serialized to JSON), then if policy.enabled runs two passes. Pass 1 (tool-result shrink): compute recent_cutoff = body.len() - keep_recent_messages (saturating), and for every message at index i < recent_cutoff whose role is "tool", call compress_tool_result, which truncates the content string to the first max_tool_result_chars chars and appends a marker \n[context edited: omitted the rest of prior {name} result; original_chars=N], returning true so stats.compressed_tool_results increments. Pass 2 (prefix drop): only if total_chars(...) > max_chars AND body.len() > keep_recent_messages, set start = body.len() - keep_recent_messages, then advance start to the first "user" message at/after that cutoff (position(role==user)), then skip any leading "tool" messages, and if 0 < start < body.len() set dropped_messages = start and keep only body[start..]. for_model_edited then prepends the system message and any non-empty system_notes as extra system messages, appends the edited body, and reports edited_chars. for_model is just for_model_edited(&[], policy{enabled:false}). compact reuses edited_body with enabled forced true and, only if something actually changed (compressed or dropped > 0), overwrites self.messages and calls rewrite_log to truncate-and-rewrite the JSONL file. The send-time view is wired in agent_loop.rs call_model, which calls for_model_edited(system_notes, &self.context_edit) before every provider chat; the destructive /compact path is the CLI's compact_session_text calling agent.session.compact.

Design rationale — why this way

The central design choice is non-destructive send-time editing: for_model_edited builds a temporary trimmed view and leaves self.messages (the canonical log) untouched, so the full transcript is always preserved for --resume and the JSONL log even though the model only ever sees a budget-bounded slice. The test context_edit_compresses_old_tool_results_without_mutating_session asserts exactly this (session keeps the 200-char original). The two passes are deliberately ordered cheap-then-expensive: tool-result truncation runs first because verbose tool outputs (shell dumps, file reads) are the dominant, lowest-value bulk in a coding agent's history, so shrinking them often gets back under budget without losing any conversational turns; only if that is insufficient does it resort to dropping whole messages. The prefix-drop is conservative: it always keeps keep_recent_messages, and rather than cutting at an arbitrary index it advances the cut to a "user" boundary and skips leading orphan "tool" messages — this preserves the OpenAI invariant that the history starts cleanly and that no "tool" message is left without its preceding assistant tool_call (a malformed prefix would be rejected by the API). compact is opt-in and only mutates/rewrites when work was actually done (the compress > 0 || dropped > 0 guard), so a no-op compact under budget leaves the log byte-identical (test compact_noops_when_under_budget). Char-counting (json_chars on serialized JSON, counting Unicode scalars via .chars().count()) is a deliberately cheap proxy for token budget — it avoids a tokenizer dependency, trading exactness for a fast, provider-agnostic heuristic. Truncation uses .chars().take(n) rather than byte slicing to avoid panicking on a multi-byte UTF-8 boundary.

Four-field config (enabled, max_chars=120k, keep_recent_messages=30, max_tool_result_chars=4k). Defaults in both session.rs Default impl and ncx-config; CLI builds it via context_edit_from_config with positive_usize fallbacks, so a non-positive config value silently falls back to the default.
edited_body (the algorithm)
Two-pass, char-budget-driven. Pass 1 compresses tool results older than the recent window; pass 2 drops the oldest prefix only when total_chars > max_chars and there are more than keep_recent_messages. Returns (body, ContextEditStats).
compress_tool_result
In-place mutation of a 'tool' message: if content chars > max_chars, replace content with head(max_chars) + a '[context edited: ... original_chars=N]' marker so the model knows truncation happened. Returns bool to drive the compressed_tool_results counter.
for_model_edited (non-destructive view)
Prepends system + non-empty system_notes (each as its own system message), then the edited body. Used on every turn via AgentLoop::call_model. Leaves self.messages intact.
compact (destructive materialization)

prefix-drop boundary safety

ContextEditStats
original_chars / edited_chars / compressed_tool_results / dropped_messages — surfaced to the user by /compact as 'chars X -> Y; compressed_tool_results=..; dropped_messages=..'.

Log is append-only JSONL with _ts stamps and inline base64 images redacted (redact_image_data). resume() reads the log, drops system rows, and sanitize_restored_messages backfills synthetic '[interrupted...]' tool replies for any dangling tool_call so resumed history is API-valid.

  • The headline distinction: send-time view (for_model_edited, every turn, non-destructive) vs. materialized compaction (compact, opt-in via /compact, rewrites the log). The full transcript is the source of truth; the model sees a budget-bounded projection of it.
  • Cheap-before-expensive ordering: shrink verbose tool results first (the bulk in a coding agent), drop whole messages only if still over budget. This minimizes conversational loss.
  • Why char counts not tokens: json_chars/total_chars use serialized-JSON Unicode-scalar counts as a tokenizer-free, provider-agnostic budget proxy — exactness traded for speed and zero dependencies.
  • API-shape invariants drive the drop logic: keep_recent floor, cut at a 'user' boundary, skip leading orphan 'tool' messages so the trimmed history never starts with a tool reply lacking its assistant tool_call.
  • Truncation marker (original_chars=N) tells the model the content was edited rather than silently lying about a short result; UTF-8-safe via .chars().take().
  • compact's change-guard (compress>0 || dropped>0) makes a no-op compact a true no-op — log stays byte-identical, verified by a test.
  • Adjacent integrity machinery: backfill_unanswered_tool_calls and sanitize_restored_messages synthesize placeholder tool replies for dangling tool_calls so interrupted/resumed sessions remain valid; log redacts inline base64 images.
Trade-offs & gotchas
  • Char-count budget is a proxy for tokens — it can over- or under-estimate real token usage depending on language/JSON overhead; there is no tokenizer in the loop.
  • Compression only applies to 'tool' messages whose content is a plain string; multimodal/array tool content or large assistant/user messages are never shrunk by compress_tool_result (only droppable via prefix-cut).
  • If the recent window (keep_recent_messages) itself exceeds max_chars, the prefix-drop guard body.len() > keep_recent_messages can leave the view over budget — the policy never trims within the kept tail, so the budget is soft, not hard.
  • Pass 2 recomputes total_chars only against post-compression body; the check uses self.system + notes too, so a large system prompt counts against the budget but is never dropped.
  • compact rewrites the whole JSONL via truncate+write; on resume the original verbose tool outputs are gone for good (the non-destructive view did not have this consequence). The marker text is the only record of what was cut.
  • positive_usize fallback means a config of 0 (e.g. someone trying to disable keep-recent) silently reverts to the default 30/4000 rather than behaving as 0.
  • Counting edited_chars by re-serializing every message on each turn is O(total history size) work per model call — fine at these scales but it is not incremental.

3Tool System & Dynamic Exposure

A single-threaded tool subsystem where every agent capability implements one ?Send async Tool trait, lives in a ToolRegistry over a cheaply-cloned ToolContext, and is exposed to the model through a dynamically-pruned, lexically-scored schema view with genome-overridable descriptions and pre/post hook wrapping.

How it works

Each capability is a unit struct implementing trait Tool (tools.rs:159), which the model sees as one OpenAI function tool: name(), description(), parameters() (JSON Schema), a defaulted read_only() returning false, and async fn execute(&self, ctx: &ToolContext, args: &Value) -> String. The trait is #[async_trait(?Send)] because the whole REPL runs on a current-thread runtime, so shared mutable state (the plan, the tool catalog/hints) uses Rc<RefCell<…>> rather than Arc<Mutex<…>>. ToolContext (tools.rs:55) is a Clone bag of everything a tool needs — workspace, SandboxPolicy, approval policy string, timeout, the shared plan, an optional Rc<dyn ApprovalHandler>, optional MemoryStore, search backend config, the tool_catalog, tool_hints, hooks, skills, and the Genome — built up via with_* builder methods. ToolRegistry::new (tools.rs:194) registers the core set (read_file, apply_patch, update_plan, shell, grep, glob, web_search, web_fetch, tool_search) and conditionally remember (only if ctx.memory.is_some()) and skill (only if skills were discovered) — capability-gating so the model never sees a tool that can't function. On register (tools.rs:229) the registry computes the effective description via genome.describe(name, tool.description()) and pushes a ToolCatalogEntry{name, description, read_only}; that catalog is what tool_search scores, so search sees the same text the model sees. Design rationale — why this way

The ?Send trait + Rc<RefCell> choice is forced by the current-thread runtime: a Send bound would demand Arc<Mutex> everywhere and buy nothing, since there is no thread to send to. Dynamic schema exposure exists because exposing every tool every turn wastes prompt tokens and degrades model tool-selection as the registry grows (MCP tools, skills, search); the constant ALWAYS_VISIBLE_TOOLS guarantees the irreplaceable core (you can always read, patch, plan, run shell, search for more tools, and load a skill) stays present, and tool_search provides the escape hatch — its results become tool_hints that surface the matched schemas next turn. The genome description-override path is deliberately a pure text-substitution surface: the training harness (ncx-forge) can evolve descriptions and the base prompt but never tool *behavior*, because the sandbox still governs execution — this keeps a candidate genome from injecting new capability and makes a failed load a guaranteed no-op (empty Genome → byte-identical schemas, asserted by a test). schema_for is a registry method distinct from the trait's to_schema() so the model-facing schema can carry the override while the trait keeps returning its unmodified default. The read_only() default of false is fail-safe: an unclassified tool is treated as a side-effecting write, never auto-batched concurrently. Conditional registration of remember/skill avoids advertising dead capabilities. The apply_patch description is verbatim load-bearing: trimming it makes the model emit git/unified-diff syntax the V4A parser rejects, looping the turn.

4Sandbox & Approval State Machine

Two orthogonal, pure-decision layers — SandboxPolicy (what's physically allowed: reads/writes/network) and Approver (what to do when an action exceeds the sandbox: AutoApprove/Ask/AutoDeny under four approval policies) — with all enforcement and prompting deliberately pushed to consumer crates.

How it works

SandboxPolicy (policy.rs) holds a mode string (one of read-only/workspace-write/danger-full-access), a normalized workspace PathBuf, extra writable_roots, network_access, and an opt-in allow_temp_write flag. can_read unconditionally returns true for all three modes (secret-file protection is left to the tool layer). can_write short-circuits: true for danger-full-access, false for read-only; otherwise it makes the target absolute against the workspace, lexically normalizes it, and returns true iff it starts_with any directory in writable_dirs() (workspace + writable_roots + system temp only if allow_temp_write). Path comparison is purely lexical via normalize (drops ., pops on .., never touches the filesystem) so a decision never depends on a path existing. The Approver (approval.rs) is a thin wrapper over a policy string; its classify(command, needs_escalation) returns a Decision enum: never -> AutoDeny if escalation needed else AutoApprove; on-request -> Ask if escalation needed else AutoApprove; on-failure -> always AutoApprove (run sandboxed first, ask only after a failure, handled upstream); untrusted -> AutoApprove only if is_trusted(command) AND no escalation, else Ask. is_trusted first rejects any dangerous_patterns regex match (rm -rf, dd, mkfs, fork bombs, etc.), then checks the first token (path-stripped, .exe-stripped) against TRUSTED_COMMANDS, and for git further rejects write subcommands in GIT_WRITE_SUBCMDS. step_decision(base, is_write, require_step_approval) layers per-step confirmation on top: it upgrades an AutoApprove write to Ask when the user disabled auto-approve, but never softens AutoDeny and never downgrades an existing Ask. Crucially, the needs_escalation input and the read-only shell heuristic (looks_read_only) are NOT in this crate — the consumer ncx-core (tools.rs ShellTool::needs_escalation) computes escalation from the policy, and ncx-tools (detect.rs) owns the conservative read-only classifier.

Design rationale — why this way

The central design decision is separating two orthogonal axes (lib.rs docs say so explicitly): the sandbox answers "is this physically allowed?" and the approver answers "what do we do when it isn't?". This mirrors Codex and lets the same policy work under different trust levels without entangling enforcement with prompting. Both layers are intentionally PURE decision functions — no I/O, no UI — because the actual yes/no prompt is an upper-layer concern (CLI=text prompt, GUI=modal round-trip, tests=canned answer), and enforcement (actually applying a patch / spawning a process) lives in the executor/tools crates. Path comparison is lexical rather than canonicalizing/symlink-resolving so that can_write is total and deterministic on non-existent paths (you must gate a file you're about to CREATE) — the doc-comment notes this matches the Python side's Path.resolve(strict=False). allow_temp_write defaults to false ("tightened default") to close a hole where the workspace itself lives under the system temp dir but a sibling temp file should still be denied. untrusted's allowlist is conservative/read-only-ish and the dangerous-pattern check runs FIRST so a trusted leading token (bare rm, or git clean) can't smuggle a destructive command past the gate. step_decision is monotone toward safety (only ever upgrades approval, never relaxes) so adding per-step confirmation can never make the system less safe.

5Tiered Orchestrator (flash / pro)

A tiered, recursive node-graph that scales effort to task risk — classify(fast) routes to single-run / plan→best-of-N-workers→verify / recursive decompose — spending a cheap+strong model pair's cost savings on structure (parallel attempts, closed verify-retry loops, divide-and-conquer) to raise completion rate.

How it works

Orchestrator::handle calls handle_at(task, 0), the recursive core (boxed as LocalBoxFuture because an async fn that recurses into itself would be infinitely sized, and ?Send/current-thread is preserved). It first runs classify — a tool-less reason(Tier::Fast, CLASSIFY_SYS, ...) whose text is parsed by parse_complexity (substring match on high/simple/medium; anything unclear defaults to Medium, the safe middle). Simple tasks take a single run(Tier::Fast, WORKER_SYS, ...) with no plan/verify. Medium runs pipeline = plan(Tier::Main) then run_attempts with self.cfg.workers (default 2) fast parallel workers verified on Fast. High, if depth < cfg.max_depth, takes decompose_and_recurse; otherwise (depth budget spent, or max_depth=0) falls back to run_attempts with high_workers (default 3) verified on Main. run_attempts is the closed loop: it launches N workers via join_all of run_worker(i, n, ...) futures (each fed the plan plus the prior round's verifier feedback by build_worker_task), runs one reason(verify_tier, VERIFY_SYS, ...) over all results, and verdict_passed passes unless the text contains 'FAIL' (fail-loud). On pass OR when rounds > max_verify_retries it parses BEST:<n> via parse_best_worker (1-based→0-based, clamped), calls promote_worker(best), and synthesize returns the best result (annotated '[unverified after retries]' if it never passed); otherwise the verdict text becomes feedback and it loops. decompose_and_recurse plans (Main), runs reason(Tier::Main, DECOMPOSE_SYS, ...), parse_subtasks (prefers 'SUBTASK:' lines, falls back to numbered/bulleted lists); <2 subtasks is atomic → best-of-N fallback reusing the plan; otherwise it truncates to max_subtasks (default 6), runs each subtask SEQUENTIALLY through handle_at(st, depth+1) (so each subtask's promoted winner is visible to the next), AND-combines all verify_passed, then does one final Main-tier verify over the joined sub-results.

Design rationale — why this way

The module docstring states the explicit premise: "The bottleneck for capability is the model, not the harness," so the orchestrator buys reliability with structure rather than a smarter model — it spends a cheap-model's cost savings on parallel attempts, verification, and decomposition. It deliberately accepts a hard ceiling: plan+verify run on Main, so it "cannot exceed the main model's reasoning ceiling" — the gains are completion-rate on simple/medium and divide-and-conquer reach on high. Effort is matched to risk so cheap tasks stay cheap (Simple skips plan/verify entirely; Medium verifies on Fast not Main). The AgentRunner trait abstracts every model call so the module is provider-agnostic and unit-testable with a scripted MockRunner (no network). The separate reason() method exists specifically so the live runner attaches NO tools to classify/plan/decompose/verify nodes — preventing a capable model from starting to *implement* the task during what should be a judgment/planning step (confirmed in runner.rs: run_in(..., with_tools=false) builds ToolRegistry::empty). Best-of-N over a cheap model is chosen as a cheaper variance-reduction lever than one expensive run. The closed verify→retry loop with feedback is bounded by max_verify_retries to cap cost; verdict parsing is intentionally lenient (substring FAIL, lenient SUBTASK/list parsing, clamped BEST) because LLM output format is unreliable and a usable result shouldn't be lost to a formatting miss. max_subtasks guards against a model that over-splits (each subtask is its own full pipeline). Recursion depth is capped (max_depth, default 1) so high subtasks that re-classify as high don't decompose forever.

Tool-less reasoning nodes (reason())

Best-of-N parallel workers + verifier selection
run_attempts spawns N independent worker futures via futures_util::join_all; each is an isolated attempt so parallel execution can't corrupt shared state. VERIFY_SYS asks for PASS/FAIL plus a 'BEST:<n>' line; parse_best_worker turns that into a 0-based index, and only that winner is promoted.
Closed verify→retry loop
On FAIL and within max_verify_retries, the full verdict text is carried into the next round as feedback via build_worker_task ('The previous attempt was rejected. Address this feedback:'). verdict_passed is fail-loud: passes unless the verdict contains 'FAIL'.
Recursive decomposition with sequential promotion
High tasks with ≥2 subtasks recurse via handle_at(st, depth+1) SEQUENTIALLY; each subtask promotes its own verifier-chosen winner to the real workspace before the next runs, so subtasks build on committed work without parallel-write collisions. Depth is bounded by max_depth, count by max_subtasks.
Workspace isolation + promotion (LiveRunner)
run_worker copies the workspace to a per-worker temp scratch dir via copy_tree; promote_worker copies the winner's scratch back onto the real workspace then deletes all scratch copies. copy_tree failure falls back to running in the real workspace (no isolation). Recursion is therefore live-safe.
Lenient parsing throughout
parse_complexity (substring, default Medium), parse_subtasks (SUBTASK: prefix then numbered/bulleted fallback via strip_list_marker), parse_best_worker (clamped, defaults to 0) — all tolerate unreliable LLM formatting so a usable result isn't lost.
Tier mapping (LiveRunner.model_for)
Tier::Main → cfg.model (pro); Tier::Fast → cfg.fast_model (flash) with fallback to cfg.model when fast_model is empty. Each node builds a fresh DeepSeekProvider + Session + tool registry (one-shot turn).

6Project Memory — Self-Evolution

A tiny markdown-backed "self-evolution" store (.ncx/memory/LEARNINGS.md) that lets the agent accumulate verified project notes and recall the most relevant ones into the system prompt as leads (not facts), using a lightweight lexical-semantic ranker plus heuristic and LLM-backed near-duplicate consolidation.

How it works

MemoryStore (memory.rs) wraps a single path .ncx/memory/LEARNINGS.md and persists MemoryEntry { ts: u64, tags: Vec<String>, text: String } records. Each entry is serialized as a parseable HTML-comment header <!-- ts:<n> tags:<a,b> --> followed by the note body; parse_entries/write_all round-trip this so the file stays human-readable and hand-editable. remember(text, tags, now) trims the text, normalizes it (whitespace-collapsed + lowercased via normalize), and skips the write if any existing entry normalizes identically (exact-text dedup returns Ok(false)); otherwise it appends, sorts by ts ascending, and drops the oldest beyond MAX_ENTRIES = 200. recall(query, max_entries, max_chars) scores every entry with semantic_score and returns a capped bullet block prefixed by RECALL_HEADER which explicitly tells the model to treat the notes as leads to verify, not facts. Scoring is a hybrid lexical-semantic sum: query keywords (lowercased, len>=3, deduped by keywords, then widened through a hardcoded domain synonym map in semantic_aliases via expanded_keywords) score +8 if they match a tag, +4 if they appear in the entry text/tags haystack; adjacent-word phrases (bigrams) add +6 on substring hit; and a Jaccard overlap of the two word sets adds up to +20 (jaccard * 20). Recency is packed into the low 6 digits (overlap * 1_000_000 + ts.min(999_999)) so higher ts wins ties, then entries are emitted until either max_entries or max_chars is hit. consolidate(threshold) is a cheap heuristic dedup run at session start: it sorts newest-first, single-link clusters by jaccard(word_set) >= threshold, keeps the newest representative of each cluster, re-caps, and is idempotent. summarize_consolidate(summarizer, threshold) does the same greedy clustering but for any multi-entry cluster asks the injected Summarizer trait (the fast-model LiveSummarizer in the CLI) to fold the notes into one concise note, keeping the cluster's newest ts and the union of its tags; if the LLM returns None/empty it falls back to keeping the newest entry, matching the heuristic.

Design rationale — why this way

The core stance (memory.rs module doc) is that memory is NOT "raised IQ" but accumulated, verified experience recalled as leads — hence the deliberately untrusting RECALL_HEADER wording and the remember tool description insisting only CONFIRMED facts be stored, keeping the store trustworthy. Plain markdown with a comment-header format was chosen over a database/embedding index so the store is human-readable, hand-editable, git-diffable, and dependency-free — consistent with the project's "tiny, no heavyweight deps" philosophy; the cost is that retrieval is lexical, not vector-semantic. To recover some semantic reach without an embedding model, the author bolts on a small hand-curated synonym map (semantic_aliases, e.g. desktop/native/window -> gui,tauri) and phrase/Jaccard signals — a pragmatic middle ground that the test recall_uses_semantic_aliases_and_tags locks in (querying "native installer release package" surfaces a Tauri/bundle note). Recency is folded into the integer score via bit-packing rather than a second sort key, giving a stable deterministic single comparator. now is passed in by the caller rather than read from the clock inside the store so writes are deterministic and unit-testable. The Summarizer trait is #[async_trait(?Send)] and dependency-injected so the core crate stays provider-agnostic and single-threaded-friendly (the whole agent is !Send/Rc-based), with the real LLM call living in the CLI's LiveSummarizer (fast model) and tests using a FixedMerger mock. Two consolidation paths exist because the heuristic is free and safe to run every startup, while the LLM merge is better-quality but costs a call — so consolidate runs unconditionally at session start (runner.rs / main.rs use 0.85) and summarize_consolidate is an explicit opt-in subcommand. The hard 200-entry cap plus char-budgeted recall (e.g. 6 entries/3000 chars in the runner) exist because recalled notes are prepended to the system prompt, so unbounded growth would blow the context window.

8ncx-forge — Harness Training Framework

A zero-GPU "scaffold optimizer": a strong-model teacher panel reflectively mutates the agent's evolvable harness (system prompt + tool descriptions = the "genome", injected via NCX_GENOME), hidden-check bench pass-rate is the fitness, and a sentinel self-check + train/val/test splits + noise-aware acceptance + Pareto small-population search guard against the dominant failure modes (silent no-op, overfitting, sampling noise), with graded trajectories exported as the bridge to actual weight training (SFT/agentic-GRPO).

How it works

The evolvable unit is the "genome": only the agent's base system_prompt and per-tool description text — never tool behavior. In Rust (genome.rs), Genome::from_env() reads NCX_GENOME=<path.toml> at startup; if unset/empty/missing/malformed/blank it returns Genome::default() (a no-op that is byte-for-byte identical to the hardcoded scaffold), and base_system_prompt(default)/describe(name, default) apply overrides only where present. On the trainer side (pure Python in train/, driving ncx.exe only via subprocess + NCX_GENOME, never importing the legacy nanocodex/*.py), the baseline genome is obtained by running ncx --dump-genome (genome.py:extract_current) so it always reflects the real tool list and the real load-bearing descriptions rather than parsed Rust source. evaluator.py:evaluate runs the agent on bench tasks in a temp workspace, grades with the hidden check.py, and — crucially — harvests a redacted FAILURE TRAJECTORY (last assistant message + tool-call names) from the agent's own .nanocodex/session.jsonl BEFORE grade() copies _check.py in, stripping any line containing grader markers so check.py never leaks to the teacher. forge.py:train is a single-champion hill-climb: each round it re-evaluates the incumbent under a fresh draw (noise-aware), feeds the top-3 failing trajectories to teacher.build_teacher_prompt, has every available teacher backend (codex/claude/api in teacher.py, each probe-gated and emitting only a TOML override block parsed by parse_candidate) propose a mutation, evaluates candidates on TRAIN, and promotes the best only if it beats the incumbent on TRAIN by accept_margin AND does not regress on the held-out VAL split; TEST is scored exactly once at the end. forge.py:evolve (M2) replaces the single champion with a small Pareto population (pass-rate↑ vs token-cost↓ via pareto.py dominance + NSGA-II crowding trim). Before any optimizing run, self_check gates execution by planting a sentinel codeword in system_prompt and asserting it surfaces with-genome but is absent at baseline. export.py writes full graded trajectories (ncx-forge-trajectory/v1) and rollout.py/finetune.py define the agentic-GRPO bridge to weight training.

Design rationale — why this way

The framing constraint is "no GPU, model is the real lever": you cannot make the base model smarter, so the framework optimizes the second lever — the harness — to use existing capability more reliably (DESIGN §1). This forces a pure text-substitution surface: the genome may change only descriptions/prompt, never behavior, because (a) the sandbox still governs execution so a teacher fed untrusted failure transcripts cannot inject new capability (a structural security boundary, DESIGN §9), and (b) it keeps the no-op guarantee provable. The no-op-on-failure default in genome.rs is load-bearing: an adversarial review found that without it, every candidate that failed to load would silently be ignored, all candidates would score identically, and the whole run would "go green" while no-opping — hence the sentinel self-check gate that refuses to train unless injection is demonstrably live. The sentinel is deterministic precisely because the original idea (a "refuse all tasks" self-destruct genome) proved unreliable: strong models ignore the refusal and complete the task anyway (compliance is noise), so a behavioral probe could not distinguish "injection dead" from "model non-compliant". The trajectory-harvesting in the evaluator exists because bench/run.py discards agent output and rmtrees the workspace, leaving the teacher to "guess from the filename" — P2 was a hard precondition. Trainer/trainee separation (Python trainer never imports the Rust trainee's legacy Python twin) keeps the only Rust change to the one NCX_GENOME injection point, minimizing conflict surface. The biggest acknowledged risk is overfitting/noise, which dictates: task-level (not run-level) train/val/test split so a task's signal can't leak across phases; grader output blanked from the teacher to prevent reward-hacking on note tails; repeats + a strict accept_margin band + per-round incumbent re-evaluation so a pure-variance +1 cannot be promoted and then frozen as "monotone improvement." Size caps are derived from the measured baseline (apply_patch ≈8125 chars and load-bearing) with a round-trip self-test, because a too-tight cap would push the optimizer to trim apply_patch and trigger a known git-diff-fallback failure loop. Pareto (vs single champion) is chosen so the search keeps a cheap-decent genome alongside a slow-strong one rather than collapsing to one point.

★ Interview talking points
  • The central design move: make ONLY text (system prompt + tool descriptions) evolvable, never tool behavior. This is simultaneously the security boundary (untrusted teacher → genome → agent with a real shell tool cannot inject new capability; the sandbox still governs execution) and what makes the no-op guarantee provable.
  • Why the no-op-on-failure default in genome.rs is load-bearing: without it a candidate that fails to load is silently ignored, all candidates score identically, and the run 'goes green' as a pure no-op — which is exactly why the sentinel self-check gate exists and is mandatory.
  • Why the gate is a deterministic sentinel codeword and not a 'refuse all tasks' genome: strong models ignore refusal instructions and complete the task anyway (compliance is noise), so a behavioral probe can't tell 'injection dead' from 'model non-compliant'. Echoing a unique codeword is deterministic and cheap.
  • The two hard preconditions found by adversarial review: P1 = NCX_GENOME injection did not exist (grep zero hits); P2 = bench/run.py discarded agent output and rmtree'd the workspace, so the teacher had no trajectory to diagnose. Both had to land before any optimization was meaningful.
  • Anti-overfit stack: task-level (not run-level) train/val/test split; grader output blanked from the teacher (prevents reward-hacking on leaked 'expected 15 got 0' note tails); per-round incumbent re-evaluation + a strict accept_margin band so a pure-variance +1 can't be promoted and frozen as fake 'monotone improvement.'
  • Self-validating TaskGen discipline: a generated task is admitted only if reference passes the check twice (determinism) AND the seed-only starting state fails it (proves real work) — the same discipline used to hand-write t1–t13, now gating machine output.
  • Cost model insight: the real cost bomb is the inner bench loop (candidates × tasks × repeats × up to 60 model turns), not the teacher calls — hence a wall-clock governor, cheap pre-screening, and budget measured in tokens/eval-count (every backend can report it) rather than USD.
  • Size caps are derived from the measured baseline (apply_patch ≈8125 chars, load-bearing) with a round-trip self-test, specifically to avoid pushing the optimizer toward trimming apply_patch and triggering a git-diff-fallback failure loop.
  • Pareto over single-champion keeps trade-offs (cheap-decent vs slow-strong) and uses NSGA-II crowding to preserve spread; the empty-eval→cost=+inf guard prevents a zero-task misconfig from silently winning the front.
  • Honest bridge to weights: the agent is a multi-turn tool loop, so vanilla trl GRPO doesn't fit — the team built an agentic rollout collector (ncx_episode reuses ncx's real loop/tools/sandbox against a vLLM-served policy) with bench_reward as a verifiable terminal reward, and the evolved system prompt can seed the RL system prompt.
Trade-offs & gotchas
  • Capability ceiling: harness optimization only improves reliability/engineering-fit; it cannot raise the base model's intelligence (plan/verify run on the main model). DESIGN states 'model is the real lever' — this is the second lever, not a smarter model.
  • Strong-baseline stall: the default scaffold already passes t1–t8, so real runs often stop at gen0 'fully solved' with nothing to mutate. Seeing teacher lift requires harder tasks (TaskGen) or starting from a degraded genome (--from-genome) or a weaker base model (--base-model/-m injection).
  • Local teacher panel is effectively single-teacher: in the author's environment claude is unauthenticated (rc=0 but is_error:true → must be judged by the structured field, not exit code), so the panel is really codex(gpt-5.4 via CLIProxyAPI proxy) + api(DeepSeek). codex model name must be resolved from ~/.codex/config.toml — hardcoded gpt-5 502s on the proxied host.
  • Trust boundary depends on redaction completeness: the grader-leak defense is substring matching on check.py/_check.py/grader/hidden test in trajectory lines; _check.py still lands in the workspace under workspace-write, so an agent that is teacher-prompted could in principle read it — DESIGN flags isolating/renaming the grader copy as a hardening TODO.
  • Pareto cost axis is a proxy when token usage is unavailable: it uses real [ncx-usage] total_tokens when ncx emits it, else falls back to mean wall-clock seconds, so cost comparisons across runs without usage are latency-based, not token-based.
  • The composed system prompt is concatenated (base + project-instructions + memory/recall + skills) but the genome only evolves the BASE segment; export.py records the genome base because ncx does not log the composed system message — the run-context suffixes are excluded from the recorded artifact.
  • run_grpo / policy_update are deliberately NotImplemented (GPU/torch); only the loop + advantage math + episode collection are tested CPU-side. The actual weight update is left as a documented contract, not running code.
  • Acceptance is by integer pass-count thresholds (accept_margin defaults to 1, repeats defaults to 1), so with few tasks/repeats the 'noise band' is coarse; DESIGN itself flags small task counts (originally 8) as the largest risk that TaskGen + splits only partially mitigate.
